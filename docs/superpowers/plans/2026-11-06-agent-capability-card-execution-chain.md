# 机器狗与智能灯 Agent Card 和执行链路整理计划

- 日期：2026-11-06
- 状态：代码实施完成，软件验收通过；真机验收待设备就绪确认
- 实施与验收记录：[定义维护位置、接口对照、修改指引和证据](2026-11-06-agent-capability-card-execution-chain-implementation.md)
- 实施顺序：先整理机器狗接入链路，再整理智能灯对外能力和调用链路
- 本次调整原则：Go2 内部同类定义尽量只维护一份，统一对外能力、请求和结果；保留两种设备各自的底层实现

## 1 先把两种设备的区别说清楚

灯的开关、闪烁和恢复等行为，需要我们在 ESP32 上编写驱动与状态转换。机器狗的站立、趴下、挥手等底层动作由已有固件实现，我们负责接入它提供的命令和反馈。

```text
智能灯：自己实现灯的状态和动作 → MQTT 接入 ──┐
                                          ├→ Agent Card → 管家或同伴请求
机器狗：调用固件已有动作并读取反馈 → HTTP 接入 ┘
```

机器狗云端还有我们自己定义的“休息、待命、互动、探索”等行为状态，用来组织任务。这些行为状态与固件提供的身体动作分别维护。

| 层次 | 机器狗 | 智能灯 |
| --- | --- | --- |
| 底层动作 | 固件实现，调用现有接口 | 我们编写 BSM 驱动和 ISM 状态转换，经 TriggerMap 接线 |
| 设备事实 | 根据实际反馈确认站立、趴卧、坐姿和动作结果 | 读取 ESP32 上报的照明状态与任务回执 |
| 云端行为 | 我们维护休息、待命、互动、探索及任务归属 | 现有模型决策、传感器上下文、调光和互动工作流 |
| 控制方式 | 遥控、自主模式、用户介入 | manual/reactive、用户让位窗口 |
| 模型决策 | 继续使用现有 LangGraph 运行能力 | 同样使用现有 LangGraph 运行能力 |

本计划同时整理 Go2 内部定义和执行组织，以及设备对外协作链路。Go2 云端的动作目录用于表达已接入的固件能力、请求条件和完成依据，不重写机器狗的运动控制器；灯继续保留自己编写的边缘状态机。

## 2 最终希望怎样使用

管家通过 Agent Card 认识设备：它是谁、会做什么、需要哪些参数、通过什么方式调用。执行过程中，管家还读取实时状态并接收执行结果，设备内部如何实现由各设备负责。

```text
设备的能力声明 → 自动生成 Agent Card
                           ↓
                 管家或同伴发现公开技能
                           ↓
                 按技能和参数发出请求
                           ↓
                 接收设备检查并执行
                           ↓
                   返回真实执行结果
```

三个信息各有用途：

| 信息 | 回答什么问题 | 来源 |
| --- | --- | --- |
| Agent Card | 设备会做什么，怎样调用 | 各设备的能力声明，经 MQTT retained 发布和注册 |
| 实时状态 | 是否在线，现在是什么状态，是否正在执行任务 | 设备反馈及已有云端运行状态，通过注册表、HTTP/SSE 等现有入口提供 |
| 执行结果 | 某次请求被拒绝、已接受、仍在执行还是确实完成 | 对应任务的实际回执和完成判断 |

Card 和状态用于帮助管家决策，权限及当前是否允许动作仍由接收设备校验。接收请求不等于完成动作。

## 3 灯暂不增加休息和待命状态

### 3.1 目前已有的状态

灯没有与狗的 `life_state` 对应的独立行为状态机。当前主要有：

- 物理状态：`OFF / ON / BLINKING / ERROR`，由 ESP32 的 ISM 管理。
- 自主模式：`manual / reactive`，决定云端是否可以自主调光。
- 控制状态：`manual / ready / holding`，由自主模式和用户让位窗口推导。
- 执行记录：现有任务、Graph 运行记录和物理回执，描述一次请求的执行过程。

它们表达不同事情。例如灯可以保持常亮，同时等待下一条命令；灯关闭时，云端仍可能在读取环境上下文并决定下一步行为。

### 3.2 本期决定

本期不为对齐机器狗而增加灯的“休息／待命”字段，也不要求每个智能体都具备狗的四个行为状态。

- 关灯不自动等于智能体休息。
- 手动模式表示暂停自主调光，仍可接收允许的命令，不能直接改名为休息。
- 用户让位窗口表示暂时尊重用户设置，不需要再复制成一个休息状态。
- 如需展示灯是否正在处理任务，优先从已有执行记录投影，避免维护另一份容易不同步的状态。

以后如果明确需要“暂停主动调光和主动社交，但继续接受用户命令”等独立行为，再单独定义进入、退出和任务处理规则。那属于灯自身的云端行为设计，不改变 ESP32 的开关、闪烁状态；是否与狗使用相同名称，要以实际语义相同为前提。

## 4 这次统一哪些内容

| 统一的部分 | 具体含义 |
| --- | --- |
| 对外能力说明 | 公开技能的 ID、说明、参数和调用方式来自明确的能力声明 |
| 请求表达 | 请求带目标、技能、参数、请求 ID 和可信执行上下文 |
| 设备侧执行边界 | 每个设备的页面命令、模型工具及同伴请求最终复用该设备的校验与执行逻辑 |
| 结果含义 | 已接受、执行中、已完成、被拒绝、失败和超时有明确区别 |
| 发现与展示 | 继续由同一份 Card 注册表提供能力信息，前端按声明展示 |

狗与灯之间不强制使用相同的内部状态名称、状态转换实现、代码类和硬件控制方式；Go2 自身重复的同类定义、判断和映射仍须按第 6.11 节集中整理。Go2 继续经 HTTP/WebRTC 实际调用，ESP32 继续经 MQTT；两者都继续使用 MQTT retained Card、status/LWT 作为控制面。

页面按钮和摇杆可以使用 Card 声明的命令绑定；同伴使用公开技能。它们最终复用设备侧执行检查，不要求每次确定的按钮命令都再经过模型解释，也不把全部内部命令开放给同伴。

## 5 分五步实施

每一步先迁移一个能快速验证的例子，再扩展到同类能力。小步提交，保护已有工作区修改；验证期间不同时运行两条会派发真实动作的旧新链路。

### 第一步 盘清接入和对外能力

- [x] 用机器狗“挥手”和智能灯“闪烁”各走一遍现有调用链，记录声明、接入命令、校验、派发和完成回执分别在哪里。
- [x] 标明 Go2 哪些是固件能力、哪些是我们维护的云端行为；标明灯哪些是边缘物理状态、哪些是云端控制状态。
- [x] 列出现有 Card 技能 ID、参数、API、MQTT topic、请求上下文和结果状态，作为兼容对照。
- [x] 定好共同的公开技能、请求和结果约定，不要求两种设备先统一内部状态机格式。

**这一步的结果：** 能清楚指出“对外公布了什么、谁实现它、谁判断完成”，并形成一张现有入口对照表。

### 第二步 精简机器狗的接入定义

- [x] 优先复用 `cloud/go2/actions.py`，集中维护已接入动作的名字、参数、固件命令映射、接入前置条件和完成依据。
- [x] 让工具参数、动作说明和 Card 从同一来源生成，减少 `card.py` 与工具注册表里的重复枚举。
- [x] 状态图生成直接读取声明，减少通过设备运行类私有字段组装 Card 的依赖。
- [x] 检查云端是否存在重复模拟固件行为的代码，按实际反馈和现有接口逐项确认职责后整理；保留请求校验和真实完成判断。
- [x] 休息、待命、互动、探索仍作为本系统的云端行为维护，声明和运行规则集中表达，不与身体动作混成一张控制表。
- [x] 不以新增或重命名 `definition.py` 为前提；优先减少重复维护和阅读跳转，再决定必要的文件整理。

**这一步的结果：** 改一个已接入动作的文案或参数范围时，工具和 Card 同步更新。配置中的动作集合与实际接入的固件能力一致，不能仅靠新增声明创造一个固件没有的动作。

### 第三步 汇合机器狗的请求和执行

- [x] 复用 `tools/executor.py`，将页面、模型工具和公开技能请求最终需要的检查与执行收敛到共同函数。
- [x] 从 `router.py` 移出混杂的设备业务处理，让 HTTP 接口主要负责建立可信上下文、转交请求和返回结果。
- [x] 共用参数、权限、连接、实时姿态、控制归属及在途动作检查；底层发送前继续复用必要的即时检查。
- [x] 保留现有 LangGraph 任务组织、检查点、任务账本、取消、超时和结果查询，不新增模型运行循环。
- [x] 同一来源及会话、同一请求 ID、相同参数的重试复用记录；相同 ID 参数不同则拒绝，新 ID 可以正常再次执行同一动作。
- [x] 保留双摇杆速度通道与急停。进入遥控不代表机器狗已移动，停止请求不直接当作已经停稳。

**这一步的结果：** 相同可信上下文下，不会因为请求来自按钮、聊天或同伴而绕过一套检查；设备反馈决定实际状态和动作结果。

### 第四步 完成 Agent Card 和多智能体调用

- [x] 各设备继续只公开明确声明的技能，Card 参数和接收方参数校验来自同一来源。
- [x] 复用 `CardRegistry`、`list_peers`、`request_peer_skill` 和现有任务结果机制，按 Card 查找技能与调用方式。
- [x] 梳理管家和同伴网关中的专用分支，集中共同的技能映射与策略；明确保留用户委托、设备自主和不同身份的权限差异。
- [x] 不因技能出现在 Card 中就扩大授权，不把内部工具自动全部公开；复用现有认证、签名及有效路由限制。
- [x] 让管家读取公开能力、必要的实时状态摘要和执行结果，不要求它读取或复制设备内部状态机。
- [x] 前端按 Card 渲染状态、转移与控件关联，移除页面内补写的设备专用语义映射；页面仍可使用同一 Card 中供展示的状态图。
- [x] 保持现有页面组织：所有状态默认完整可见、转移箭头可见、媒体仅放大为有界窗口、移动节点提供双摇杆。

**这一步的结果：** 管家和设备能通过 Card 发现许可范围内的能力并完成调用；只有真实完成结果才允许继续依赖动作。

### 第五步 整理智能灯并验证复用

- [x] 以开关、调光、闪烁三个现有能力逐一整理，复用 `tool_registry.py`、`tool_executor.py` 和物理任务账本。
- [x] 硬件配置与能力发现继续来自 `UNIT_CONFIGS` 和 manifest；边缘 ISM 保持物理转换的执行依据，云端不新增替代边缘 ISM 的物理状态机。
- [x] 校验 manifest 对应的固件版本契约、云端工具参数和 Card 声明一致。处理当前固件声明的重复维护，同时保留旧固件兼容，不直接删除版本表。
- [x] 页面、灯 Graph、管家和同伴请求最终复用灯自己的物理任务执行边界，再经 MQTT 派发，依据 ESP32 回执返回结果。
- [x] 保留 `adjust_lighting` 语义入口，让现有灯 Graph 决定颜色和亮度，再调用同一物理执行入口，不增加硬编码调色规则。
- [x] 保留 manual/reactive、用户让位窗口、同伴请求处理和云端离线本地规则；本期不新增灯的休息／待命行为状态。
- [x] 保留 BSM、ISM、TriggerMap 的职责及现有同步主循环。传感器继续独立发布状态和事件，不生成设备卡。
- [x] 两种设备跑通后，只提取实际重复的能力说明、技能解析或结果契约辅助代码，不建设新的通用设备框架。

**这一步的结果：** 灯的能力说明、参数和实际固件对应；闪烁在收到完成并恢复原状态的回执后才算成功。机器狗与灯通过相同的外部协作约定工作，各自内部实现保持清楚。

## 6 机器狗详细实施方案

这一节将前面的第二、三、四步展开到文件、调用路径和提交顺序。整理的重点是现有固件能力的接入，不实现新的步态、平衡控制或动作轨迹。

### 6.1 先分清三类状态

| 类别 | 包含内容 | 谁负责 |
| --- | --- | --- |
| 固件提供的动作和身体事实 | 站立、趴卧、坐姿、挥手、舞蹈及实际运动 | 固件负责执行；云端发送请求、接收反馈并形成可信的状态投影 |
| 本系统的云端行为 | 休息、待命、互动、探索、任务归属和用户介入 | `state.py` 与现有行为执行代码维护 |
| 调用和控制过程 | 请求接受、执行中、完成、超时；遥控方式、自主模式、连接与反馈新鲜度 | 任务记录、控制上下文和连接适配维护 |

不能把云端身体状态记录当成机器狗的运动控制器，也不能把它全部删掉。接收方仍需知道当前是否有可靠站立反馈、是否正在执行上一个动作，以及一个结果能否确认。若固件反馈没有直接提供所需的姿态或完成标识，保留已有观测适配；固定等待时间和 RPC 接受都不能替代完成证据。

四个主行为按当前约定继续表达：

| 行为 | 含义 | 需要保持的规则 |
| --- | --- | --- |
| 休息 | 暂停自主活动，保持连接和当前已确认姿态 | 进入前检查正在进行的动作、导航和遥控；普通身体命令需先唤醒 |
| 待命 | 没有正在接纳的互动或探索任务 | 可以在状态和权限允许时接纳下一项任务 |
| 互动 | 正在处理一项用户或同伴任务 | 模型一轮结束不自动代表实体动作已经结束 |
| 探索 | 正在执行已接纳的探索任务 | 停下观察时仍可保持探索；停止和唤醒都不重放旧任务 |

自主模式、主行为和身体事实分别保留。例如“允许自主探索＋当前待命＋身体站立”是正常组合。

### 6.2 文件职责和具体处理

| 文件或目录 | 保留的职责 | 需要整理的内容 |
| --- | --- | --- |
| `cloud/go2/actions.py` | 已接入动作、参数、SDK 映射及完成策略的目录 | 补齐应共用的动作说明和显示信息，减少其他文件重复枚举 |
| `cloud/go2/state.py` | 当前事实、云端行为、任务归属和状态快照 | 集中云端行为的来源、目标及条件，避免同一个规则散在多个入口 |
| `cloud/go2/connection/fsm.py` | 观测适配、可用动作查询和接入校验 | 从动作目录读取约定，清理重复判断；保留新鲜度和完成确认 |
| `cloud/go2/connection/webrtc.py` | 实际 SDK 调用、回调、速度与停止 | 不再接受上层绕过共同检查的调用；发送前保留必要的即时检查 |
| `cloud/go2/connection/sensors.py` | 接收设备原始反馈 | 保留已有采样、连接归属与观测输入，不因目录整理改变识别算法 |
| `cloud/go2/tools/registry.py` | 内部工具的名称、参数、角色和结果要求 | 从动作目录生成运动参数；集中工具与公开技能的关联元数据 |
| `cloud/go2/tools/executor.py` | 参数、权限、租约和设备执行边界 | 让按钮和模型工具复用相同的动作执行函数，而不仅是调用同一个检查函数 |
| `cloud/go2/tools/tools.py` | 工具到具体业务或设备调用的适配 | 消除工具再回调 HTTP 路由执行业务的反向依赖，动作派发使用共同入口 |
| `cloud/go2/router.py` | HTTP 接入、可信上下文、SSE 和任务接口 | 逐项移出动作或行为业务，保留现有 URL 和入参兼容 |
| `cloud/go2/card.py` | Card 组装及 MQTT card/status/state 发布 | 生成函数读取动作与工具声明，移除私有运行表依赖及重复能力说明 |
| `cloud/go2/tasks.py`、`control.py`、`execution.py` | 任务记录、会话归属、控制租约和执行上下文 | 统一关联和调用，避免再建立一套平行的任务或权限系统 |
| `cloud/agents/go2/graph.py` | LangGraph 规划、工具选择、检查点和回复 | 工具和公开技能从统一声明解析，调用现有执行边界 |
| `cloud/api/intents.py` | PWA 命令入口及设备服务转发 | 保留命令别名及用户身份，不另写设备业务条件 |
| `cloud/agents/steward/tools/`、`cloud/peers/gateway.py` | 管家和同伴请求的接入、协作策略与路由 | 使用当前 Card 解析能力，合并共同策略，保留不同身份与来源的授权差异 |
| `app/src/pages/` 与 `app/src/utils/stateMachine.js` | 通用白板、预览和控件 | 只消费 Card 的状态图、控件关联与实际状态，不自行推导 Go2 的业务转移 |

先减少重复清单、反向依赖和分散的业务分支，不为了文件名整齐把现有模块再拆成大量小文件。需要改函数归属时，同时检查它读写的模式、任务和连接状态归谁维护。

### 6.3 动作和公开技能分别在哪里定义

按三层组织已有声明，避免一个名字在三个文件分别手写：

```text
动作目录 actions.py
  Hello / SDK 映射 / 参数 / 接入条件 / 完成依据
                  ↓
工具注册表 tools/registry.py
  go2_sport / cmd 枚举 / 工具权限 / 公开技能关联
                  ↓
Card 生成 card.py
  公开技能 + 参数说明 + 供页面使用的状态和控件声明
```

以挥手为第一个迁移例子：

| 信息 | 当前含义 | 整理后的维护位置 |
| --- | --- | --- |
| 动作 ID | `Hello` | 动作目录，保持兼容 |
| 固件调用 | 现有 `api_id=1016` 映射 | 动作目录，适配器读取 |
| 接入前置条件 | 当前连接、可靠站立、无冲突任务及有效权限 | 目录描述允许来源，运行层复用实时判断 |
| 请求目标 | 执行挥手，预期回到站立 | 动作目录；目标不直接写成已发生的事实 |
| 完成依据 | 沿用当前已实现的设备观测确认策略 | 动作目录引用策略，观测层提供证据 |
| 对外技能 | `go2_sport`，参数 `cmd=Hello` | 工具声明关联公开技能，Card 从中生成 |
| 页面名称和预览 | 挥手及对应示意 | 从声明生成，不在前端另列动作清单 |

具体实施项：

- [x] 盘清 `ActionSpec` 现有字段，优先扩展已有目录，不复制一个新动作注册表。
- [x] `SPORT_COMMANDS`、模型工具参数枚举和 Card 的动作参数从目录生成。

- [x] 对话入口单独声明：`go2_chat` 没有对应硬件动作，也不应被当成普通工具名查找。

读取底层 SDK 编号和控制通道只发生在设备适配中；管家和同伴不需要读取这些字段。

### 6.4 各种请求如何汇合

| 入口 | 现有主要路径 | 目标接线 |
| --- | --- | --- |
| 页面动作按钮 | `/api/commands/go2` → `/api/go2/commands` → 检查 → `send_command` | 原接口转交同一个设备动作执行函数 |
| 狗的自然语言对话 | `/api/go2/chat` → Go2 Graph → `execute_tool` → 工具实现 | Graph 负责理解和规划，工具最终调用同一个动作执行函数 |
| 管家调用公开技能 | 读取当前 Card → 技能验证 → HTTP 技能请求 → Go2 Graph | 按声明解析固定技能，沿用任务和结果机制，再进入同一个设备执行边界 |
| 灯或其他同伴请求 | `request_peer_skill` → 同伴网关 → Go2 技能任务 | 同样按 Card 解析，保留可信来源与协作授权，不直接控制 WebRTC |
| Go2 自主工作流 | 现有 Graph 或工作流 → 工具执行 | 沿用原来的自主上下文，复用相同设备检查 |
| 遥控和急停 | 速度接口、停止接口 | 保留低延迟通道和独立停止能力，不绕到聊天模型 |

拟在现有 `tools/executor.py` 内收敛一个设备动作执行函数，由路由和工具共同调用。函数名和参数以实施时的现有调用约定为准，职责顺序确定为：

```text
接收规范化命令及可信上下文
    → 校验命令、参数、身份和请求有效期
    → 检查连接、行为状态、姿态反馈及在途动作
    → 检查控制归属和已有请求记录
    → 登记本次请求，再调用设备适配
    → 记录接受、执行或完成结果
    → 返回原有兼容字段及关联 ID
```

要合并的是分散的实现和规则来源。HTTP 的身份校验、设备执行前的业务检查、真正发送时的即时检查各自仍有必要，不能只保留首次检查而忽略排队期间发生的状态变化。

具体实施项：

- [x] 先迁移页面 `Hello` 和工具 `go2_sport(cmd=Hello)`，验证两条路径只派发一次且条件一致。
- [x] 再迁移其他预定义动作；保持参数拒绝方式、租约和原命令 ID。
- [x] 整理 `perform_life_control` 的业务归属，让工具不再回调 `router.py` 执行业务；模式和导航副作用通过现有适配代码访问。
- [x] 收拢 `prepare_user_interaction` 等介入处理的调用时机，避免同一请求被多层重复中断或重复接纳成互动任务。
- [x] 固定技能与自由对话分开解析。`CHAT` 进入自然语言任务；具体技能进入已解析的工具调用，复用已有 `initial_tool`、`allowed_tools`、`tool_guard` 和 Graph 执行能力。
- [x] 为 Card 的 `go2_chat` 增加完整接入验证：当前声明中的 `tool_name=None` 必须作为对话入口处理，不能落入“未知公开工具”的判断。

### 6.5 云端行为怎样整理

保留现有行为条件，集中声明和执行接线，不增加一套新的 Agent 循环。

| 请求或事件 | 保留的主要条件 | 成功后的含义 |
| --- | --- | --- |
| 休息 | 待命、稳定姿态、有效反馈，无在途动作和运动任务，已退出遥控 | 暂停自主活动，保持当前已确认姿态 |
| 唤醒 | 已连接且当前休息 | 回到待命，不自动恢复之前的探索 |
| 开启探索 | 当前可活动、可靠站立、无冲突任务，满足管理员及定位地图条件 | 设置现有探索许可与运行配置；不直接声称身体已经移动 |
| 停止探索 | 检查任务归属，管理员覆盖继续沿用既有策略 | 停止对应探索，清理归属与许可；物理停稳仍由反馈确认 |
| 接纳互动任务 | 当前可接纳且执行上下文有效 | 记录互动任务及所属会话 |
| 互动结束或取消 | 匹配原任务及连接代次，检查相关实体动作是否仍未确认 | 满足条件后回待命，不由模型回复结束直接解锁下一动作 |

具体实施项：

- [x] `LIFE_ACTIONS`、工具参数、Card 行为转移和 API 允许集合使用同一来源。
- [x] `Go2State` 维护行为事实及任务归属，执行层处理导航、视觉消费者和模式切换的副作用。
- [x] 盘清 `_autonomy_mode` 与运行快照中的模式字段，明确一个维护位置，其他入口读取或投影，避免各自写一份模式。
- [x] 保留 `epoch`、任务归属和完成关联。旧任务、旧连接的结果不能结束新任务或改写新姿态。
- [x] 对休息、探索的失败做无副作用验证：请求在前置检查被拒绝时，不先取消现有任务或改变租约。

### 6.6 反馈与完成判断保留什么

| 信息 | 能证明什么 | 处理方式 |
| --- | --- | --- |
| 指令成功发出 | 请求进入传输 | 返回接受，不直接改变为目标姿态 |
| RPC 返回接受 | 固件接受了该请求 | 记录接受或执行阶段，继续等待支持的完成证据 |
| 可靠姿态观测 | 当前身体事实 | 更新姿态与观测时间，不等同于所有在途动作都成功 |
| 符合本次动作确认条件的反馈 | 本次动作的实际完成 | 记录完成、释放相关等待和任务状态 |
| 无法确认、反馈过期或超时 | 结果仍未确认 | 保持明确的未确认结果，不猜测站立或自动重发 |

现有姿态识别、关节或运动反馈适配属于云端接入职责；它们并非固件运动控制代码，不能以“狗已有状态机”为由直接删除。遥测缺少请求 ID 时，沿用连接代次、动作记录与观测关联，不能把旧 progress 或高度样本当成本次动作的完成回执。

- [x] 保留 `body_state=None` 表达没有可靠姿态，不重新引入“姿态待确认”状态节点。
- [x] 保留 `body_confirmation`、观测时间和新鲜度，界面与执行层读取同一份快照。
- [x] 保留 `pending_action` 与 `last_action` 的阶段、目标、结果和确认依据，不能因模型一轮结束而清掉尚未确认的实体动作。
- [x] 区分拒绝请求、执行失败、取消请求、停止请求和已确认完成，避免统一包装成 `ok`。

### 6.7 任务记录和停止通道怎样接

当前聊天任务已通过 `ChatTaskRegistry` 关联会话、参数和结果；直接 `/commands` 请求没有相同的外部任务 ID 入口。迁移时要补齐这处关联，不能把聊天任务已有去重能力视为所有按钮请求都已具备相同能力。

- [x] 复用现有任务记录、Graph 检查点和 `FileEffectLedger`，为直连动作补充可关联的请求身份；不另起平行任务系统。
- [x] 原接口保留兼容，新增关联字段按可选扩展处理；旧调用由服务端生成新请求身份。
- [x] 派发前登记，同一来源和会话下的同 ID 同参重试查询已有记录，同 ID 异参拒绝，新 ID 同参正常执行。
- [x] 崩溃或断连后只有派发记录、没有实际结果时，保留结果未确认，不因恢复过程自动再次调用设备。
- [x] 保留 HTTP 任务查询、Graph 步骤、同伴请求和设备动作记录之间的关联，不强行把生命周期不同的 ID 都合成一个字段。
- [x] 保留 `trace_id`、任务 ID、步骤 ID 与设备请求记录，能从一条用户请求查到实际派发和结果。

三个停止情形单独回归：

| 情形 | 必须保留的行为 |
| --- | --- |
| 松开摇杆 | 对应速度分量归零，两个摇杆全部松开后为零向量 |
| 退出遥控或普通停止 | 调用已有停止路径，退出控制方式，实际停稳以反馈为准 |
| 无姿态反馈或动作未确认时急停 | 急停入口保持可用，不被普通动作忙碌状态或状态同步等待阻断 |

### 6.8 Card 与协作策略怎样收尾

- [x] 每个公开技能能在工具或对话入口中找到实际接收实现，生成时检查映射完整性。
- [x] Card、模型工具和接收方使用同一份参数定义；SDK 编号、内部函数和设备访问令牌不需要暴露给管家。
- [x] 同伴视图保持公开技能加必要状态摘要，页面使用同一 Card 中的状态图，不把整张 UI 配置灌入模型。

- [x] 复用现有受验证的 transport、签名和 HTTP 接入限制。消费 Card 不意味着可以把内部令牌发送到任意声明地址。

### 6.11 Go2 定义统一的范围和硬性验收

目标是以后修改一个已有动作、行为或公开能力时，能找到明确的定义位置，相关消费者自动同步。整理范围覆盖 Go2 自身、狗的 Graph、Card、管家和同伴接入，以及前端中的 Go2 专用定义，不能只在 `cloud/go2/` 内去重后就宣布完成。

#### 每类内容明确一个维护位置

| 内容 | 维护位置与整理要求 | 其他模块怎样使用 |
| --- | --- | --- |
| 身体状态、固件动作及映射 | 以现有 `actions.py` 为动作目录，集中动作 ID、文案、参数约束、允许来源、预期结果和完成策略引用 | 工具、观测适配、Card 和执行器读取；保留不同动作各自的实现 |
| 云端行为及转移条件 | 以 `state.py` 为行为规则的维护位置，集中行为名称、行为命令和转移条件；副作用仍由执行层负责 | API、工具和 Card 复用规则或其声明投影，不分别再写一份转移表 |
| 模式、当前状态及任务归属 | 以现有运行状态为事实来源，G1 逐字段确认维护方，收拢重复可写变量 | HTTP/SSE、MQTT 摘要、Card 运行字段和界面读取投影，不能各自修改一份 |
| 工具、公开技能与调用参数 | 内部工具在 `tools/registry.py` 声明，公开技能关联集中维护；对话入口单独明确 | 模型工具、Card 和接收方校验使用同一参数约定；公开子集明确筛选 |
| 请求、执行结果与拒绝原因 | 复用 `models.py`、任务记录及共享结果契约；G1 确认各层已有类型和字段的语义 | 路由和 Graph 做显式转换；同一执行结果不因入口不同而改变含义 |
| 执行条件与权限策略 | 设备业务检查汇入现有执行边界，协作策略明确唯一维护方 | 各入口使用可信上下文调用；发送前可重新检查，来源不同的授权差异明确保留 |
| 页面名称、转移线、动作预览及控件绑定 | 设备语义从上述声明生成并由 Card 提供；可复用预览资源按 ID 关联 | 页面保留布局、缩放和交互实现，不再手写另一套状态名称、动作集合或转移关系 |
| 多处共用的超时、限值和默认值 | 按参数语义归到已有动作、工具或对应模块配置；G1 列出重复项并确认是否确为同一参数 | 消费者引用定义；数值碰巧相同但用途不同的参数不强行合并 |

这里的“一个维护位置”按信息类别确定，不要求把所有内容塞进一个大文件。Card 是生成的能力说明，不能成为另一套手工配置；导航、视觉和连接算法继续在各自模块实现，与动作目录通过明确接口关联。

#### 在既定提交顺序中落实

- [x] G1 交付“定义—现有位置—目标维护方—消费者—迁移方式”清单，覆盖上表各类；特别记录重复枚举、前端映射和同义字段。
- [x] G2～G7 每迁移一类定义，同时迁移其消费者；保留旧名称时只做明确别名或格式转换，不保留可独立修改的第二份定义。
- [x] G8 按 G1 清单逐项清理旧定义、重复判断和无用转发；确需保留的重复检查说明其发生时机与用途。
- [x] 最终交付简明的 Go2 修改指引：改动作、行为转移、公开技能、参数限值、预览和执行实现时，分别从哪里开始，何时确实需要修改适配代码。

#### 用实际修改验证统一效果

| 验收修改 | 应自动同步的内容 |
| --- | --- |
| 修改已有动作名称或说明 | 页面和 Card 更新，模型使用相同说明，不修改已有兼容 ID |
| 修改已有动作参数范围 | 按钮或控件参数声明、工具 schema、Card 和接收方校验一致 |
| 修改一个云端行为转移条件 | 实际允许结果与 Card/页面声明保持一致；运行条件由同一规则提供 |
| 调整一个公开技能的参数或关联 | 管家发现、同伴发现和接收方解析一致，不手改多份技能清单 |
| 修改一个共用超时或限值 | 对应消费者引用同一来源；不同阶段的超时保持各自语义 |

以上修改用模拟和契约检查验证；修改声明本身不会新增固件能力、生成新算法或绕过权限。仅让接口字段看起来一致、保留背后多份可独立修改的定义，不算完成本节目标。

## 7 怎样验收

| 场景 | 应得到的结果 |
| --- | --- |
| 修改一个已接入动作的文案或参数范围 | 工具、Card 和校验同步，减少手工修改多份清单 |
| 相同上下文从页面、聊天或同伴请求动作 | 共用该设备执行边界，不因入口变化绕过校验 |
| 未声明的技能、非法参数或权限不足 | 明确拒绝，不派发到硬件 |
| Go2 没有可靠姿态反馈 | 保持空姿态，不高亮虚构状态，不开放依赖该姿态的动作，急停仍可用 |
| 请求已接受但动作未完成 | 返回接受或执行中，依赖步骤继续等待 |
| 超时、取消、断线及请求重试 | 不自动重放动作，不误报完成，可查询已有记录 |
| 用户再次发起同样动作 | 新请求 ID 正常执行，不误判成旧请求重试 |
| 双摇杆同时操作和分别松手 | 平移与转向合并，分别松手清零对应分量，全部松手归零，退出停止 |
| 管家要求先闪灯两次再让狗挥手 | 在权限和模式允许时，先等待灯的真实完成，再请求狗并等待狗的真实结果 |
| 灯关闭或常亮但没有在执行请求 | 不把开关状态或没有任务自动改称休息／待命 |
| 灯处于手动或用户让位窗口 | 保留现有控制语义，不额外切换一套行为状态 |
| 手机打开设备页 | 全部状态在视口内，转移线可见，媒体浮窗不全屏 |

软件检查用模拟设备和回执覆盖声明一致性、执行校验、协作调用和布局。真机验收另行记录 Go2 设备反馈、ESP32 回执与跨设备执行顺序，模拟通过不记作真机通过。

## 8 兼容和交付

保留现有命令 ID、公开技能 ID、API 路径、MQTT topic 和可信上下文字段。Card 的能力发现、status/LWT 和运行快照仍来自现有控制面，Go2 长任务不阻塞编排器的 MQTT 事件循环，PWA 继续使用同源 API/SSE。

实施前记录现有检查结果和关键调用样例。过渡接口只转发到同一实现，不复制业务规则或重复派发；迁移完成后清理无用转发和重复定义。回退时恢复对应代码和由其生成的 Card，避免 retained 声明与执行逻辑不一致。

最终交付包括 Go2 定义维护位置清单及修改指引、精简后的 Go2 能力接入、每个设备各自明确的执行入口、可靠的 Agent Card 协作链路和智能灯的同链路验证。底层状态机的统一重写和灯的新行为状态不在本期范围内。
