# SSM 三智能体人格、性格与行为改进计划

> 日期：2026-10-30  
> 状态：待评审；本文只规划，不改运行代码或驱动设备  
> 范围：在原 Go2 人格/行为/回复计划上，扩展至 `cloud_orchestrator`、`esp32_desk_led`、`go2` 及各自的 PWA 设置入口  
> 调研依据：[成熟 AI 角色与人格设计调研](../../research/2026-10-30-ai-character-personality-systems.md)  
> 关联：[同伴主动交互计划](2026-10-27-personality-driven-peer-interaction.md)只负责同伴发信；本文统一人格配置、个体行为与面向用户的回复

## 目标和统一原则

三个智能体使用**同一套配置契约、同样的 `agentcore/personality/` 目录职责、同一类读写 API 与前端编辑组件**。每个智能体可以有不同的身份文案和特质维度；特质必须标出其影响的具体决策点。人设影响回复内容与模型参与的行为判断，特质影响已存在的行为机会或偏好。配置变更后无需重启，下一次决策读取新快照。

物理动作依旧由各设备原有的权限、模式、执行器、FSM、地图和反馈检查。人格不能把 `accepted / timeout / blocked` 说成完成，也不能替 Go2 越过运动安全检查。编排器依旧只协调和派发，不因“主动”特质绕过用户意图自主控制设备。

## 当前基线与缺口

| 智能体 | 现状 | 需要补齐 |
| --- | --- | --- |
| 编排器 | `agentcore/prompts.py` 中硬编码 `AGENT_PERSONA`；`graph.py` 和 `multitask.py` 引用；有 MQTT card，但当前 `/api/devices` 只投影加入空间的设备 | 可持久化人格/特质、统一读取接口、个人设置入口；不把编排器伪装成待接入物理设备 |
| 灯 | `agentcore/soul.py` 管理 `prompt` 与 `social_initiative`，已有设置抽屉；文字进入聊天和 reactive 提示词 | 迁入统一目录和配置格式；展示参数含义及实际生效位置；保留默认 manual 和用户让位逻辑 |
| Go2 | `agentcore/soul.py` 管理人格文案、三个特质及每日演化；已有设置抽屉；外向性接入同伴交流 | 好奇心/大胆程度目前多停留在文案；固定探索计数与好奇心未接线；部分失败和早退回复仍是固定系统文案 |

原 Go2 计划中的具体缺口保留：`free_explore.py` 用固定 `_CURIOSITY_THRESHOLD = 10` 的计数触发移动探索，和 `traits.json.curiosity` 没有直接联系；`boldness` 主要体现在生成的文案。`agent.py` 的正常成功回复使用人格化 responder，但 `accepted / timeout / blocked / cancelled` 等路径提前返回固定文本；连接失败、权限拒绝、模型不可用时也可能直接返回系统文案。它们的事实表述可靠，角色声音却不一致。现有控制租约、FSM、`user_interrupt`、地图与定位新鲜度检查继续作为行为边界。

## 最小统一结构

```text
cloud/agent_runtime/personality.py                # 共享 Profile/trait 校验、序列化与事实回复契约
cloud/orchestrator/agentcore/personality/
    profile.py                                     # 管家默认值、存储路径、读写
    behavior.py                                    # 管家的特质 → 澄清/回复偏好
cloud/esp32/agentcore/personality/
    profile.py                                     # 灯默认值、读写、旧数据迁移
    behavior.py                                    # 灯的特质 → reactive/社交偏好
cloud/go2/agentcore/personality/
    profile.py                                     # Go2 默认值、读写、旧数据迁移及每日演化入口
    behavior.py                                    # Go2 的特质 → 探索/互动候选
cloud/api/personality.py                           # 三者统一管理端点，不放业务逻辑
app/src/components/AgentPersonalitySettings.jsx   # 统一的人设与特质编辑区
```

每个 `profile.py` 对外提供相同接口：`get_profile()`、`update_profile(changes, context)` 和 `get_trait_specs()`。共享代码只负责类型、范围、原子保存和只读快照；每个智能体的 `behavior.py` 负责把分数解释为**本智能体已有的决策偏好**，不创建跨智能体的万能行为引擎。原有 `soul.py` 的调用点逐步改为引用本目录，迁移完成后删除重复逻辑。

统一配置视图：`{agent_id, prompt, traits, trait_specs, revision}`。`traits` 是 `{参数名: 0..100}`；`trait_specs` 给前端提供中文名称、说明、默认值、取值范围和“影响什么行为”的简短解释。每个智能体可以有不同的特质键。人设文案和数值都必须真正进入对应的决策或回复路径；没有消费点的参数不出现在设置页。运行时配置存于各智能体已有数据目录下的 `personality/profile.json`，一智能体一份；文件内另留非 UI 的演化元数据。旧灯 `soul/personality.json` 与 Go2 `soul/{personality,traits}.json` 首次读取时兼容迁移，迁移必须幂等、保留管理员修改及 Go2 的 `last_evolved`。编排器新增自己的数据目录和默认文件，从当前常量初始化。

API 进程和编排器目前通过同一仓库路径启动为不同进程。编排器配置由 API 校验并原子写入其持久化目录，编排器每次意图读取最新快照；部署时两进程必须指向同一持久化卷。若以后拆到不同主机，再单独设计配置同步，不把设备卡或 MQTT retained 消息当作人格存储。修改人格不改变 Agent Card 的技能或在线状态。

## 各智能体的差异化人格与可见参数

下表是第一版的**计划参数**，默认值与映射阈值在实施时以现有行为为基线回放确定；不提前写死新的运动参数。

| 智能体 | 人格文案方向 | 特质与实际消费点 |
| --- | --- | --- |
| 编排器 | 温暖、简洁的空间管家；忠实传达用户目标 | `warmth`：聊天、确认及结果回复的语气；`clarification_tendency`：仅在意图或必要参数确有歧义时，影响先问清还是按已知信息继续规划；任务有效性仍由固定规则决定 |
| 灯 | 略带吐槽但礼貌、擅长照顾桌面照明 | `social_initiative`：沿用现有活动内主动交谈机会；`adjustment_sensitivity`：仅在 `reactive` 模式影响对环境变化是否重新评估调光，不把分数直接映射为 RGB 或亮度；manual 和用户让位优先 |
| Go2 | 好奇但有分寸的探索伙伴 | `curiosity`：空闲时探索评估机会；`extraversion`：沿用当前 `social_initiative` 的同伴交流机会，并影响有人互动时的表达；`boldness`：在允许的观察、姿态、转向候选之间影响先观察还是行动，不改变速度、导航许可或避障 |

三个智能体的人格文案都应同时写明“是谁、怎样说话、遇到不确定情况通常怎样处理”，保持简短。人设是可编辑的表达与倾向数据，不能包含授予权限或覆盖固定规则的指令。行为偏好在模型提示词中明确引用当前数值；无需模型的决策点由 `behavior.py` 读取同一数值。人格改变后若某条路径无法体现差异，应在设置页说明该参数的作用范围，而不是宣称它全面控制智能体。

## 同一回复契约，保留不同角色声音

三个智能体的用户可见回复遵循同一流程：**真实结果摘要 → 本智能体人格与特质 → 自然语言回复 → 事实校验或保守回退**。常规对话、动作成功、部分成功、受理未完成、阻止、超时、取消、离线及模型不可用都覆盖。中途进展若以该智能体身份发出，也使用相同的配置快照。Go2 原计划提到的 `agent.py` 早退、`multitask.py` 和自主模式回复共同遵守该契约；同一结果只做一次人格表达。不能只让成功回复人格化，失败回复却变成统一系统腔。

结果摘要只来自执行记录；`ok` 才能说完成，`accepted / executing / timeout` 只能说明尚未确认；失败和拒绝不能说成已执行。模型不可用时使用各智能体自有的简短事实模板，保证身份口吻与状态准确；模板不推断用户偏好或未来动作。编排器负责交代整体安排，不模仿灯或 Go2 的口吻；设备动作结果仍由对应设备自己表达。

例如地图不可用时，Go2 可以说“我现在看不清能安全走的路，先待在这儿。”，不能说“我已经过去啦”。这只是验收场景示例；具体措辞由当前人设决定，不将示例写成所有失败场景的固定台词。灯与编排器对同一类未确认结果也分别使用自己的口吻。

## API 与 PWA 设置入口

- 管理端统一使用 `GET /api/agents/{agent_id}/personality` 和 `PUT /api/agents/{agent_id}/personality`，`agent_id` 仅允许上述三个已知智能体。GET 返回统一视图；PUT 只接受 `prompt` 与本智能体已声明的 `traits`，拒绝未知键、越界值、旧 `revision`，并复用现有管理员鉴权/CSRF。保存成功返回新视图；旧灯/Go2 路由在过渡期转接同一实现，避免两套写入逻辑。访客不能读取私人配置或写入。
- 灯、Go2 原有“设备设置”入口继续存在，改为复用 `AgentPersonalitySettings`。每个页面展示当前人格文案、所有实际生效的特质数值、范围、作用说明和保存结果；Go2 的 `social_initiative` 直接显示为“外向性”的同一值，不出现两份滑杆。设置保存在现有抽屉中，记忆/地点仍各归原处。
- 编排器使用独立的“管家”页面或入口，在其**自己的**设置区复用同一组件。当前首页设备列表只包含加入空间的物理设备；需为 `cloud_orchestrator` 增加明确的系统智能体入口或独立页面路由，不能依赖把它加入物理设备列表。设置页需能显示离线时最后保存的配置；保存权限仍需管理员在线会话。
- PWA 从 API 的 `trait_specs` 渲染控件，不在 JSX 中硬编码三个智能体的特质枚举。页面加载、修改、保存、重开后值一致；失败时保留未保存的输入并显示原因。

## 实施顺序与验收

1. **统一配置层。** 建共享契约及三个 `agentcore/personality/` 目录，迁移旧数据，替换旧 `soul.py` 和硬编码 `AGENT_PERSONA` 的读取点。验收：三份配置同形、各自默认值正确；Go2 每日演化仍只更新自己的资料，管理员编辑不会被并发覆盖；编排器无需重启即可在下次意图中使用新资料。
2. **三条行为接线。** 编排器澄清偏好、灯 reactive 敏感度、Go2 好奇心/大胆程度接入已有决策点；保留已实现的社交主动性。验收：同一输入下改变参数能观察到对应候选/跳过差异；无权限、manual、用户停止、地图无效时，任何性格都不能触发越界动作。
3. **回复一致性。** 三个智能体的成功与异常路径使用同一事实契约和各自的人格；覆盖直接返回的系统文案。验收：同一真实状态不会因人设变化被误报；修改每个智能体的人设后，聊天、成功和失败回复都保留各自身份。
4. **设置可见。** 统一 API 与前端编辑组件，接入灯、Go2、管家三个页面；旧路由兼容。验收：每页都能查看并编辑自己的人格与全部生效参数，重载后仍一致；访客不能写，未知智能体不能写，旧客户端数据不丢失。
5. **现场核对。** 先回放或模拟各类决策和结果：Go2 分别覆盖探索/跳过、成功、受理未完成、阻止、超时、取消、断连和模型不可用；灯覆盖 reactive/manual 与用户让位；管家覆盖闲聊、歧义澄清及任务反馈。随后只在现有导航闭环有效的条件下，于可随时停止的场地短距离验证 Go2。记录配置 revision、决策、执行反馈和回复，能追溯“哪个性格值影响了哪次选择”，同时确认回复仍像同一个角色。

每一步按项目现有节奏控制在可快速验证的粒度。第一版不引入情绪引擎、复杂角色卡、MBTI、额外 LLM 角色层或新的设备运动能力。
