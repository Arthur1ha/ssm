- 日期：2026-11-06
- 状态：计划草案，待用户审阅；本轮不实施功能代码
- 项目：SSM / Go2
- 本期目标：统一连接、活动、生活、身体状态；补齐指定动作；同步 PWA 展示与控制
- 工作量：约 6–10 人日，含针对性自动验证及一轮真机联调

## 1. 交付目标与范围

本期完成后，用户能够看到机器狗是否在线、是否休息、当前在待命/互动/探索中的哪一种生活状态，以及身体姿态或动作；可以通过页面和现有聊天入口操作新增动作、休息、唤醒与探索。所有入口服从同一套状态约束和实际执行反馈。

本期按用户提供的分层并行状态图组织业务。图表达的是正常业务状态；连接失效、姿态未知、命令失败和反馈超时另有明确的运行契约，不通过虚构成功状态掩盖。

### 1.1 本期必须交付

1. 统一状态契约和单一运行快照。
2. 连接、活动、生活、身体状态及其合法转移。
3. 新增 `Sit`、`RiseSit`、`Content`、`FingerHeart`、`FrontPounce`、`FrontJump` 六个命令。
4. 旧动作、遥控、导航、探索、互动接入新状态契约。
5. 休息、唤醒和用户介入时的任务交接。
6. Agent Card、MQTT 状态摘要、HTTP 查询和 SSE 的一致表达。
7. PWA 分层状态展示、并行高亮、新动作示意及控制反馈。
8. 兼容迁移、针对性回归、真机反馈矩阵和验收记录。
9. 为后续条件/动作编排落实稳定状态 ID、动作 ID、转移入口与事件语义。

### 1.2 本期不实施

- 自然语言创建、修改、启用休息/唤醒条件。
- 时间调度、无人持续时长、多条件组合等规则执行能力。
- 用户命名动作组合、动作序列编辑器、循环或分支编排。
- 拖拽修改基础身体状态机或新增任意底层命令。
- 新的 Agent 运行框架、第二套决策循环或独立记忆系统。
- 更换模型、人格、长期记忆机制和导航算法。
- 额外扩充用户未指定的动作、翻转或步态。
- 精细骨骼动画、视频动作素材或图像生成。
- 改造 ESP32 的状态机与灯的自主行为。

“为后续编排准备”只落实当前改造必需的契约，不提前建设完整规则引擎。

## 3. 不变的架构约束

### 3.1 现有大脑继续负责决策

- 继续使用 `cloud/agents/go2/graph.py` 与现有自主工作流。
- 继续使用 LangChain 工具调用、LangGraph、文件检查点、动作账本和共享回复契约。
- 模型继续理解用户意图、选择工具、观察结果并组织人格回复。
- 只更新状态上下文、能力声明、必要提示词和工具适配。
- 状态模块只校验转移与维护已发生的事实，不生成新的计划或人格决策。
- 若休息/唤醒需要多步骤适配，使用现有执行和 Graph 能力；不增加自研 Agent 循环。

### 3.2 传输与设备发现继续沿用

- MQTT retained card/status 仍是能力发现和在线真相来源。
- Go2 实际调用继续经 HTTP，动态展示继续经现有 SSE。
- MQTT state 摘要、HTTP、SSE 来自同一份快照，不各自维护业务状态。
- 编排器不能因 Go2 的长动作同步阻塞 MQTT 事件循环。
- PWA 继续无构建运行，不新增 MQTT 直连或设备状态轮询。

### 3.3 原有执行约束继续生效

- 复用 `ExecutionContext`、控制租约、任务归属和现有权限策略。
- 副作用动作串行；读状态、视频和对话不因此全局阻塞。
- 指令已发送、设备已接受、动作已完成分别表达。
- 超时、断连、取消、服务重启不自动重放身体动作。
- 页面和模型调用都不能绕过后端状态校验。

## 4. 目标状态模型

### 4.1 状态维度

| 字段（拟定） | 值 | 语义 |
|---|---|---|
| `connection_state` | `offline / connecting / online` | 控制连接是否存在 |
| `activity_state` | `active / rest`，离线时为空 | 在线期间是否可活动 |
| `life_state` | `idle / play / explore`，休息或离线时为空 | 当前生活行为目的 |
| `body_state` | 12 个业务状态；另允许 `unknown` | 身体姿态或动作 |
| `autonomy_mode` | 保留现有 `manual / free_explore` 接口值 | 是否允许按现有自主策略发起行为 |

活动状态与现有“空间活动”不是同一概念，内部命名与接口文档要明确区分，不能拿空间 `activity_id` 代替可活动/休息状态。

`autonomy_mode` 是配置，`life_state` 是运行状态。允许自主探索时，也可以正在互动、待命或休息；不能通过一个模式值推断当前生活状态。

本期保留 `free_explore` 的 API 值，避免同时引入自主模式重命名迁移。前端文案明确它表示允许自主探索，而非保证此刻正在移动。

### 4.2 并行与层级关系

```text
连接
├─ 离线
├─ 连接中
└─ 在线
   ├─ 休息
   └─ 可活动
      ├─ 生活区域：待命 / 互动 / 探索
      └─ 身体区域：站立 / 趴下 / 坐下 / 移动 / 各种动作
```

生活与身体区域同时生效。例如 `explore + standing` 表示探索过程中停下观察，`play + greeting` 表示互动中招手。

用户图中身体区域位于 Active 内。实现仍需在休息时保留身体观测，否则“休息中 · 趴下”无法表达。这里保留的是身体事实与上次确认记录；休息期间不开放普通身体动作转移。

### 4.3 身体业务状态全集

| 状态 ID | 展示名称 | 类型 |
|---|---|---|
| `standing` | 站立 | 稳定姿态 |
| `lying` | 趴下 | 稳定姿态 |
| `sitting` | 坐下 | 稳定姿态 |
| `moving` | 移动中 | 运动状态 |
| `greeting` | 招手中 | 有限动作 |
| `stretching` | 伸展中 | 有限动作 |
| `content` | Content 执行中 | 有限动作 |
| `dancing1` | 舞蹈 1 中 | 有限动作 |
| `dancing2` | 舞蹈 2 中 | 有限动作 |
| `finger_heart` | 比心中 | 有限动作 |
| `pouncing` | 前扑中 | 有限动作 |
| `jumping` | 前跳中 | 有限动作 |

`Content` 暂保留用户给定名称；确认实际动作表现前不自行翻译成可能误导的名称。

### 4.4 运行辅助信息

仅增加执行与展示确实需要的信息，字段最终随阶段 A 契约收敛：

- 当前动作、来源、关联 task/run ID、请求目标和执行阶段。
- 状态来源与确认时间，区分身体观测和命令目标。
- `control_mode`：普通/遥控，用来解耦遥控入口和实际移动。
- 身体状态可信度：已确认/等待确认/未知。
- 可用动作与不可用原因。
- 快照版本：进程/连接代次与单调递增 revision，避免旧事件覆盖新状态。
- 最近一次转移的事件、原因及关联任务，写入已有日志/事件机制。

这些信息不新增“正在思考”“开心”等生活状态，不把导航任务状态、Graph 节点和身体状态合并。

## 5. 核心转移与默认行为

以下是供本次审阅的默认语义。实施前通过契约和测试固定，后续不在代码不同位置自行解释。

### 5.1 连接与初始化

| 事件 | 处理 |
|---|---|
| 发起连接 | `offline → connecting`；不可发运动命令 |
| 连接成功 | `online + active + idle`；身体先同步真实反馈 |
| 连接失败 | 回到离线，保留错误原因 |
| 断连 | 立即关闭运动入口；取消所属任务；身体标为未知，历史确认姿态单独保留 |
| 重连 | 建立新代次，丢弃旧等待者/回调；不恢复未完成动作和旧导航 |
| API 进程重启 | 从当前连接和真实反馈重建；不凭旧快照宣称站立或恢复任务 |

图中的初始站立是正常业务路径。实现不能再把 WebRTC 成功直接当作站立证据；同步前显示“姿态待确认”。如果坐姿没有可靠遥测映射，不用身高阈值强行将其判为站立。

姿态未知时仍允许诊断读取、急停、断开和重新同步。若固件无法报告可靠姿态，使用外部遥控完成可观察的姿态恢复后再同步；不能为了让页面解锁而猜测站立，也不顺带增加未获指定的新恢复命令。阶段 A 必须识别是否存在这一硬件反馈缺口。

### 5.2 休息与唤醒

| 事件 | 前置条件 | 成功结果 |
|---|---|---|
| 请求休息 | 在线、可活动、生活待命、身体为已确认稳定姿态、无未完成身体动作或导航、控制权允许 | `active → rest`，生活区域不再激活 |
| 忙碌时请求休息 | 正在互动/探索/移动/有限动作中 | 返回阻止原因；不隐式排队、强制取消或稍后偷偷执行 |
| 唤醒 | 在线休息、权限与控制权允许 | `rest → active + idle` |
| 休息期间普通动作 | 尚未唤醒 | 阻止，提示先唤醒 |
| 休息期间急停/断连 | 任意 | 仍可处理，不因休息门禁失效 |

本期“休息”表示保持 WebRTC 与状态上报、暂停自主活动，不表示关机、断网或切换底层电机模式。

默认休息保持当前稳定身体姿态，不自动附加 StandDown；默认唤醒也不自动起立。这样休息/趴下、唤醒/起立保持独立，后续用户才能组合“先趴下再休息”或“唤醒后招手”。

休息期间自主运动和普通自主互动不启动。保留必要状态与事件通道，但本期不接入自动唤醒规则；“看到主人就醒来”等属于下一期。

唤醒进入待命，不立刻重放休息前的动作或导航。自主性配置可以保留，但休息前的探索意图不自动恢复，需要显式开启探索。

### 5.3 生活状态

| 当前状态 | 事件 | 目标状态/约束 |
|---|---|---|
| 待命 | 进入用户互动任务 | 互动 |
| 互动 | 相关任务结束/取消/失败 | 待命；旧任务回调不得结束较新的互动 |
| 待命 | 开启探索 | 探索；须满足现有自主模式、权限和导航前置条件 |
| 探索 | 停止探索 | 取消所属导航、处理停步结果后回待命；清除继续探索意图 |
| 探索 | 用户介入 | 停止/交接所属运动后进入互动；停步未确认时不开始下一身体动作 |
| 任意可活动生活状态 | 断连 | 生活状态失效，不保留为当前态 |

补充约束：

- `play` 表示已接纳的用户互动/明确互动任务，不取代长期人格、情绪或社交内驱动。
- 同伴游戏等既有互动任务可以映射到 `play`，不另建第二套互动执行器。
- 查询状态、预览节点、打开页面不改变生活状态。
- 等待用户补充的任务必须有明确的任务归属，不无限占用运动控制权。
- 普通互动结束只转待命；若原自主配置和任务策略仍允许，后续是否再探索由现有自主入口决定。
- 用户明确“停止探索”、急停、进入休息或模式关闭后，不因普通互动结束自动重启探索。
- 探索启动失败、没有可执行任务时不能长期挂在“探索中”；根据实际结果回待命并说明原因。
- 生活状态由任务接纳和收尾事件驱动，不能只在 HTTP 请求开始/结束时机械切换，尤其要覆盖异步任务和澄清恢复。

### 5.4 身体转移

| 来源 | 命令/事件 | 目标 | 说明 |
|---|---|---|---|
| 站立 | `StandDown` | 趴下 | 真实反馈确认 |
| 趴下 | `StandUp` | 站立 | 真实反馈确认 |
| 站立 | `Sit` | 坐下 | 新增 |
| 坐下 | `RiseSit` | 站立 | 新增 |
| 站立 | `Move`/有效遥控输入 | 移动中 | 不因进入遥控就宣称移动 |
| 移动中 | `StopMove`/确认停止 | 站立 | 命令接受与停稳证据分别处理 |
| 站立 | `Hello` | 招手中 | 完成或有效停止后回站立 |
| 站立 | `Stretch` | 伸展中 | 完成或有效停止后回站立 |
| 站立 | `Content` | Content 执行中 | 完成后回站立 |
| 站立 | `Dance1` | 舞蹈 1 中 | 完成或有效停止后回站立 |
| 站立 | `Dance2` | 舞蹈 2 中 | 完成或有效停止后回站立 |
| 站立 | `FingerHeart` | 比心中 | 完成后回站立 |
| 站立 | `FrontPounce` | 前扑中 | 完成后回站立 |
| 站立 | `FrontJump` | 前跳中 | 完成后回站立 |

不直接开放趴下→跳舞、坐下→移动、一个有限动作→另一个有限动作等未声明转移。组合请求由现有 Graph 按真实结果逐步选择合法路径，不由底层执行器静默补动作。

“动作中”需要已下发并有可用开始依据；等待下发或只知道请求目标时在执行阶段显示“等待设备反馈”，不能把最终姿态当作已确认当前态。

### 5.5 遥控、移动与导航

- `EnterMoveControl` 保留兼容入口，主要改变 `control_mode`，零速度时身体仍可站立。
- 有效速度输入使运动进入移动状态；结合现有遥测确认状态和停稳，不把传输接受当成物理证据。
- 摇杆归零可以停步并保持遥控入口；退出遥控释放对应控制状态。
- 正在坐下、趴下、休息、姿态未知或有限动作未结束时，不能进入普通移动。
- 导航与摇杆通过同一执行门禁，不能并发争用运动；保留现有 deadman 和速度限制。
- 导航的 idle/going_to/patrolling 及任务结果继续保留，作为任务细节，不扩充生活基础状态。

### 5.6 急停与普通动作取消

- 急停入口始终可达，先阻止后续自主运动并取消所属任务/速度流。
- 普通取消只按动作目录声明的中断能力处理，不能默认所有新动作都支持 StopMove 中断。
- 不把软件停止请求等同于真实姿态恢复；没有确认时保留未知/未确认结果。
- 坐下/趴下时急停不强行写成 standing，也不自动起立。
- 动作无法即时中断时明确表达停止请求和真实反馈结果，不假定能在空中切换姿态。
- 各入口复用现有停止和租约机制，不另建一套紧急控制通道。

### 5.7 操作权限与任务归属

| 操作 | 默认权限/归属 |
|---|---|
| 读取状态、预览动作 | 保持现有已认证读取权限；预览不占控制权 |
| 六个新增即时动作 | 沿用现有即时动作角色范围，必须通过控制租约、生活门禁和身体转移校验 |
| 请求休息、唤醒 | 作为当前设备的即时控制，沿用现有可介入用户权限与控制权规则；不写持久自主配置 |
| 开启探索 | 沿用现有自主模式切换的管理员要求，或已验证的空间活动所有者内部入口；不能借新命令绕过权限 |
| 停止本会话探索/运动 | 按现有任务取消与控制权规则执行，不结束其他会话无关任务 |
| 急停 | 保持现有授权用户的紧急停止语义，不要求先获得普通运动租约 |
| 保存自动条件/持久自主配置 | 本期不新增规则保存能力；既有管理员边界保持 |

生活状态切换不是绕过控制权的旁路。空间活动拥有的探索、用户会话任务和自主任务的归属应沿用现有标识，不以一个无来源的全局布尔值取代。

## 6. 统一动作定义与反馈契约

### 6.1 动作目录

拟新增 `cloud/go2/actions.py`，集中定义本期支持的动作。文件名可在阶段 A 随模块边界调整，功能范围固定。

每个动作至少声明：规范命令、中文名称、底层目录/命令映射、允许来源姿态、执行态、预期完成姿态、完成证据类型、超时、普通中断能力及必要参数。

由此生成或校验：

1. 身体状态机转移与动作可用集合。
2. `go2_sport` 的参数枚举和工具说明。
3. 命令网关即时动作允许集合。
4. Card 状态图、动作标签和静态能力。

用户测试过的六个新命令纳入同一目录；不顺带开放底层库其他命令。保留 StopMove、Move 和 EnterMoveControl 的不同职责。

### 6.2 每项动作必须记录的反馈信息

| 项目 | 要记录的内容 |
|---|---|
| 指令映射 | 实际使用 SPORT 还是其他已验证目录、命令名/API ID、参数 |
| 下发响应 | 传输和设备响应码；响应在开始还是结束时到达 |
| 开始依据 | progress、模式变化或其他已验证信号 |
| 完成依据 | 实际能证明该动作结束的信号 |
| 结束姿态 | 是否确实回站立，坐姿/起身如何确认 |
| 可中断性 | 支持何种停止方式，停止是否有独立确认 |
| 缺失反馈 | 缺帧/无完成信号时返回什么结果，如何解除未确认状态 |

优先读取 `cloud/go2/data/action_probes/` 下已有记录和用户现有测试事实；不自动执行交互探测脚本。确需补测的项目仅列入明确的真机验证步骤。

不能仅凭动作名推断使用哪一套底层命令表。若用户验证走的是 MCF 等目录，沿用已验证的具体映射，不静默切换设备模式。

### 6.3 结果与恢复

- 沿用现有 result 枚举，不为新状态另起一套任务结果协议。
- 保留可追溯的 `confirmation`，必要时增加其范围：请求接受或动作完成。
- RPC code=0 只有在对应协议/实测确实代表完成时，才可作为依赖动作的完成依据。
- 不使用“等待固定 N 秒→假定回站立”的统一完成策略。
- progress 必须属于当前动作和当前连接代次；旧样本不能完成新任务。
- 坐下与趴下不能只因身高接近而混淆；没有可靠模式映射时标为未确认。
- 超时后先按动作支持的方式收尾，不自动重发，不隐式开始下一动作。
- 某动作能运行但没有完成证据时可以表达 accepted/未确认；验收必须注明这一限制，不能标为可靠串联通过。
- 若新的姿态确认语义影响旧动作，必须同步更新旧测试和网关返回，不能只让新页面理解新结果。

## 7. 状态所有权、发布与兼容

### 7.1 单一事实来源

拟新增 `cloud/go2/state.py` 作为统一快照和受约束转移模块：

- 连接适配更新连接事实。
- 传感器/动作确认适配更新身体事实。
- 现有任务入口/收尾更新生活状态及归属。
- 生活控制入口更新活动状态。
- 自主模式仍走现有模式管理，仅向快照同步。

其他模块读取快照或投递已验证事件，不随意直接写多个状态字段。`connection/fsm.py` 继续提供身体层规则；统一状态模块不依赖具体页面，也不调用模型。

状态提交保持短小；取消任务、等待硬件等长操作不能持有状态锁。需要多步交接时携带任务 ID/代次，完成时重新核对归属，防止旧任务收尾覆盖新任务。

### 7.2 动态快照示例

以下是示意，非提前锁定全部字段：

```json
{
  "unit_id": "go2",
  "state_schema_version": 2,
  "epoch": "本次服务或连接代次",
  "revision": 42,
  "connected": true,
  "connection_state": "online",
  "activity_state": "active",
  "life_state": "play",
  "body_state": "greeting",
  "body_confirmation": "observed",
  "autonomy_mode": "manual",
  "control_mode": "normal",
  "fsm_state": "greeting",
  "available_actions": ["StopMove"],
  "ts": 1793930400
}
```

运行状态版本与 Card 能力描述版本分别管理。时间戳不用于同代次内的唯一排序；新 epoch 的连接不能被旧快照 revision 压制。

### 7.3 HTTP、SSE 与 MQTT

- 保留 `/api/go2/connection` 与 `/api/go2/connection/stream`，增量扩展字段。
- 增加生活控制操作，经现有 `/api/commands/go2` 网关路由到 Go2 服务；具体命名在阶段 A 确定，例如 request_rest、wake、start_explore、stop_explore。
- 状态变化主动触发现有 SSE，不等下一帧硬件遥测才显示生活状态。
- MQTT 状态摘要保留 `unit_id`、连接、分层状态、版本与 `ts`，不塞入大图、视频或模型文本。
- 不新增 MQTT 控制面真相或改变主题结构；在 `protocol/topics.md` 增补 Go2 state 字段说明。
- Card 是静态能力和状态结构声明，实时值来自 state/SSE，不在构卡时复制一份当前值。
- 队列过载时可合并为最新快照，不能阻塞传感器回调；快照不依赖客户端收到全部事件才能恢复。

### 7.4 向后兼容

- 保留 `connected`、旧端点、旧动作名和 `fsm_state`，至少覆盖本次迁移窗口。
- `fsm_state` 从新快照单向投影：离线/连接中保留旧占位，在线时投影身体状态；不能成为第二个可独立写入的状态源。
- 对旧字段 setter、测试 stub、Agent 提示词和导航校验逐一迁移，不能留下双向同步循环。
- 旧端点保留不等于保留“接收命令即假定完成”的错误语义，相关返回变化需文档化。
- Card 的分层区域采用可选字段扩展；老平面图继续可渲染，灯不需要修改。
- 新前端读旧 Card 时回退平面展示；旧前端读新 Card 时保留身体层基础展示。
- 未知状态显示待确认，禁止因为缺字段回退成可操作的站立。
- 前端缓存升级需验证，不能让旧脚本与新 Card 长期混用。

## 8. 前端展示与交互设计要求

### 8.1 页面结构

1. 顶部状态摘要：例如“在线 · 可活动 · 互动中 · 招手中”。
2. 活动层：可活动/休息，以及休息/唤醒操作。
3. 生活区域：待命、互动、探索，显示当前态与合法转移。
4. 身体区域：12 个状态，显示实际姿态/动作与可执行操作。
5. 状态图说明：生活与身体同时有效；展示两处高亮，不拼成大量组合节点。
6. 原有视频、地图、摇杆和聊天保留适当位置。
7. 原有设置中的自主模式保留，但说明与生活状态的关系。

手机优先采用生活与身体分区、上下排列；较宽屏幕可并列。层级关系由容器和标签表达，不强求在小屏完整绘制所有嵌套边框。

### 8.2 状态图声明

- 扩展 Card 状态图的区域/父级/对应 state_field 信息。
- 复用现有 FsmGraph 渲染单个区域；组合层只负责层级和多个当前态。
- 保留现有顶层平面字段作为身体图兼容投影。
- 休息时生活区域不高亮，身体事实可见，但普通动作禁用。
- 不在 React 中另写一份动作允许表；使用后端快照和 Card 声明。
- 已声明转移与运行时可用性分别处理，禁止仅因画有连线就允许执行。

### 8.3 控制反馈

- 选择/预览节点不发命令、不改变实际状态。
- 点击转移才派发命令；重复点击同一未完成请求不能重复触发身体动作。
- 指令处理中显示等待/执行状态，不提前高亮最终姿态。
- 被阻止时解释具体原因：休息中、需先站立、当前动作未结束、控制权冲突、姿态未确认等。
- accepted、完成、超时、失败和断连分别显示。
- 生活控制成功等待同一快照同步；HTTP 返回不能长期覆盖更新的 SSE。
- 急停保持易触达；普通取消不伪装为所有动作都可中断。
- 断连后所有普通运动操作失效，页面显示连接问题而非冻结成仍在执行。
- 键盘可访问、触控目标、颜色以外的状态提示和减少动画偏好纳入验证。

### 8.4 新动作示意

- 扩充 `StateVisual.jsx` 的 SVG：坐下、Content、比心、前扑、前跳。
- 起身复用站立姿态，命令过程通过执行状态表达。
- 图像是动作示意，不冒充实时视频或真实姿态识别。
- 无需 imagegen、外部图片或新构建依赖。
- 检查 12 个节点在移动端的标签、点击区域、缩放与图例，不把所有标签挤在同一画布。

所有阶段按依赖顺序实施，不拆出独立 Agent。每个任务以一次可检查的小改动为单位，先自动验证再连真机；不在一个未验证的大改动中同时替换所有入口。

## 12. 已识别风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 新动作没有完成信号 | 无法可靠串联 | 先核对已有记录，逐动作定义反馈；无法确认则明确未确认，不伪造通过 |
| Sit 与趴下遥测相似 | 错误放行动作 | 结合可靠模式与实际动作确认；没有证据保持未知 |
| 大量旧代码读写 fsm_state | 双状态源、遗漏门禁 | 全仓盘点、单向投影、测试覆盖旧入口 |
| 生活任务晚到回调 | 新任务被旧任务收尾覆盖 | task ID、代次和控制归属核对 |
| 休息关闭过多后台任务 | 无法状态同步或将来无法唤醒 | 保留连接/观测边界，只门禁自主活动 |
| 自主模式与探索状态混淆 | 唤醒后意外探索或展示错误 | 配置和运行状态分开，明确停止/恢复语义 |
| 摇杆归零被当作退出遥控 | 控件跳变 | control_mode 与 body_state 分离 |
| STOP 被当成站立确认 | 坐姿/跳跃期间显示虚假姿态 | 停止请求、结束姿态分别确认 |
| 公共 Card 扩展影响灯 | 跨设备回归 | 可选区域扩展与旧平面渲染回退 |
| 前端缓存与新字段混用 | 展示错误/动作重复 | 兼容读取、快照版本、缓存升级验证 |
| 原有教导可绑定但运行路径受限 | 被误认为已实现通用编排 | 本期只回归已有路径，新增规则能力另列下一期 |
| 真机/环境暂不可用 | 验收延期 | 先完成模拟和浏览器验证，硬件项单独标记，禁止宣称全部完成 |
