# Go2 Air 指定地点导航闭环计划

> 日期：2026-10-28  
> 状态：待实施；本文只规划，不改运行代码或让机器狗移动  
> 范围：Go2 的地图、定位、目标、路径执行与结果反馈；`reactive` 保持原地反应，`free_explore` 复用同一导航闭环

## 目标与边界

用户说“去门口”后，SSM 应在同一张有效地图上确定机器狗与门口的位置，规划已知可通行路线，持续根据实测位姿调整，最后仅在确认停稳且抵达目标时报告成功。不能规划、定位丢失、被阻挡、超时或用户接管时，应停止并报告对应结果。

**机身继续负责已有的近距离避障和底层行走。** SSM 不新增一套避障算法，也不绕过机身避障服务。SSM 负责地图定位、全局路径、目标选择、进度与到达判定；机身避障触发停步或绕行后，SSM 根据实际位移判断是否继续、重规划或结束。实施前只核实当前运动模式下机身避障确实启用，不以“服务存在”代替现场验证。

当前 Go2 Air 不能依赖 `uslam` 作为上述导航后端：2026-10-28 的 WebRTC 实测中，机身成功响应 `robot_state` 服务报告请求，连续 6 次返回 23 项服务，包括 `unitree_lidar`、`voxel_height_mapping`、`obstacles_avoid`，没有 `uslam_server`；5 个 `uslam` 状态/地图 ID 查询均无回包，而普通雷达位姿持续到达。因此本计划按**外部地图与定位**设计；若以后机身固件或算力配置改变，再以接口回包和实机到达测试评估是否切换。

## 当前基线

| 环节 | 已有能力 | 当前限制 |
|---|---|---|
| 数据 | `connection/webrtc.py` 订阅 `rt/utlidar/robot_pose`、压缩体素图、机身路径话题；`sensors.py` 提供位姿与点云快照 | 未给导航提供位姿/地图新鲜度、质量与统一坐标系契约；机身路径话题存在不代表机身 SLAM 在运行 |
| 地图 | `occupancy_grid.py` 从体素点云生成 2D 障碍位图；实机消息为 `frame_id=odom`、分辨率 0.05 m、128×128 格，约 6.4 m 见方 | 这是当前局部观测，未形成可持久化、带未知区域的全局地图；未提供重启后的地图定位 |
| 地点 | `memory/spatial.py` 可保存当前位置为命名地点，`/navigation/locations` 可读写 | 只存 `x/y/heading/ts`，无 `map_id`、坐标系和定位置信度；现有 `home` 保存于 2026-06-23，不能直接认定仍有效 |
| 规划 | `frontier.py` 给探索方向生成短距目标；`astar.py` 搜索栅格路径；`navigator.py` 跟随并在卡住后重试 | 未观测区按空地处理、允许对角切墙角、目标格可被截到地图边界；无路或无地图会降级直线行走；规划和跟随可能使用不同瞬时栅格 |
| 执行 | WebRTC 速度控制、停止接口、控制租约、会话打断 | 导航速度命令没有逐条应用层失联看门狗；随机后退/转向逃脱没有确认退路；周期重规划实际落在 6 秒卡住检查分支内 |
| 结果 | 距离阈值 0.3 m、朝向对齐、`go2_navigate_to` 工具、`/navigation/state` | 单次位姿接近就可报到达；朝向对齐超时仍可能报成功；`/navigation/go` 立即返回“开始”，状态不含最终结果；工具固定 25 秒超时 |
| 模式 | `free_explore` 可调导航器；`reactive` 只做姿态和转向 | 探索提示允许“看到远处物体就标记”，实现却把**狗当前位置**存为该物体地点，产生语义错误 |

## 实施顺序

每阶段只改变一处可验证行为，先用离线回放或模拟输入验证，再在开阔、有人可接管的场地做短距实机测试。保留当前工作区其他未提交改动。

### 阶段 0：先让现有导航诚实且可停止

**涉及：**`navigation/{navigator,occupancy_grid,astar,frontier}.py`、`agentcore/mode/free_explore.py`、`agentcore/tools/tools.py`、`router.py` 及对应 Go2 测试。

- [ ] 无有效点云、位姿过期、目标越出已知地图、A* 无路时返回 `blocked`/`localization_unavailable`，不退回直线导航或定时前进。面向探索的短距方向目标也受相同门槛约束。
- [ ] 为位姿和点云保存接收时刻、原始时间戳、`frame_id`；停止使用过期或不同坐标系的数据。`odom_to_grid` 对导航路径返回明确越界，不静默截断。
- [ ] 栅格区分 `free/occupied/unknown`；未知区不可作为已知安全路径。按机身实际外形和安全余量配置膨胀；只在当前实测机器人足迹处清理自体点，不能固定清理地图中心。
- [ ] A* 禁止对角穿过障碍角；目标落障碍或未知区时只允许在**同一可达自由区域**内选择邻近停靠点，并把实际停靠点展示给用户。规划与跟随共享同一份地图快照；地图变化后再显式重规划。
- [ ] 修正周期重规划与卡住检测的独立计时；卡住后先停，再判断重规划，禁止无退路证明的随机后退。速度控制加入心跳/失联停止机制，保留已有 `/stop` 与会话接管。
- [ ] `free_explore` 的 `go2_tag_location` 只表示狗**已经站到**该地点；远处视觉发现记为观察，不写进可导航地点。临时探索目标不需要写入持久地点文件，可直接传坐标给导航器。
- [ ] `go2_navigate_to` 不再只凭返回文本前缀判成功；`/navigation/go` 返回任务 ID，`/navigation/state` 显示 `accepted/executing/succeeded/blocked/failed/cancelled`、失败原因、最后可信位姿与目标。

**验收：**无图、过期图、越界目标、未知区和障碍封路均不产生前进指令；用户停止或断连后有明确停止结果；原地邻近目标不会凭单帧噪声报成功。此阶段只承诺**同一有效 odom 会话内的短距导航**，不宣称跨重启到达。

### 阶段 1：固定传感器与坐标契约

**涉及：**`connection/sensors.py`，新增 `navigation/pose_provider.py`、地图诊断数据结构；修复 `/map/debug` 序列化，保留 `/map.png`。

- [ ] 在不让狗自主移动的条件下，记录点云、雷达位姿、IMU 的频率、时间戳、`frame_id`、地图原点随狗移动的关系及断连/重启后的原点行为。确认机身避障在当前速度控制模式下的实际效果。
- [ ] 明确 `odom`（短期连续）、`base`（机身）、`map`（持久地图）的坐标变换及单位；所有导航输入附带帧、时间、质量和地图版本。位置估计不可用时不创建任务。
- [ ] 判定 WebRTC 的压缩体素数据是否足够做稳定的离机地图匹配。若不足，先接入机身可提供的带时间戳原始雷达数据/本地数据通道；**不得拿滚动栅格坐标冒充地图定位结果**。

**验收：**同一位置的重复采集在坐标上可解释；故意断开/重连会让定位状态降为不可用；地图诊断端点可返回不含 NumPy 原生对象的结构化快照。未取得足够观测数据前，阶段 2 不开始导航实机验收。

### 阶段 2：持久地图与重定位

**涉及：**新增 `navigation/map_store.py`、`navigation/localization.py`，调整 `occupancy_grid.py` 和 `memory/spatial.py`。

- [ ] 人工遥控走过测试区域，构建并保存一张含障碍、自由区、未知区、分辨率、原点、`map_id` 和版本的地图；保存与加载要可校验，损坏地图不可用于导航。
- [ ] 用当前雷达观测与保存地图匹配，并结合短期里程计持续估计 `map → odom`；输出位置、朝向、时间戳和置信度。算法实现按阶段 1 的数据质量选成熟匹配方案；匹配不可靠时返回 `unlocalized`，而非继续使用旧变换。
- [ ] 地点改存 `map` 坐标和 `map_id`。旧 `spatial.json` 坐标保留但标记为 `legacy_unanchored`，包括 `home`，需在新地图中重新标定；不自动把旧 `odom` 坐标解释成新地图坐标。
- [ ] 每次重启、断连后重新定位；若起始位姿无法自动确定，提供管理员在地图上设初始位姿并现场确认的入口。定位完成前禁用“去指定地点”。

**验收：**关机/重启后仍能在保存地图上定位到同一测试点；人为把狗放到另一个位置时不会继续使用旧位姿；地点的 `map_id` 不匹配时拒绝导航。实测记录误差与定位失败率，再定下一阶段的速度和到达阈值。

### 阶段 3：全局路线、局部执行与到达闭环

**涉及：**`navigation/navigator.py`、`connection/webrtc.py`、Go2 工具与路由、PWA 导航状态展示。

- [ ] 只在当前 `map_id` 的已知自由区规划全局路线。机身负责近距离避障；SSM 通过进度和位姿判断被挡、偏离、停滞，并有限次重规划，超过预算即停止并返回 `blocked`。
- [ ] 控制器按新鲜地图位姿跟踪路线；限制速度、转角、任务时长和最大偏航。指令失联、定位质量下降、地图不一致或接管时立刻停止，不继续发运动命令。
- [ ] 到达必须同时满足：位置误差在阈值内、所需朝向在阈值内、连续多个新鲜观测稳定、停止指令已执行且机身基本停稳。任一条件未满足不得写 `succeeded`。目标被修正到邻近停靠点时明确报告“到达停靠点”，不冒充到达原坐标。
- [ ] 任务结果从导航器传到 `/navigation/state`、`go2_navigate_to`、设备页与编排器；调用方只在终态 `succeeded` 时向用户说“已到达”。固定 25 秒等待改为任务 ID 查询与明确的运动期限，避免外层超时而狗仍在走。

**验收：**在标定区域做同一次会话的 1 m、2 m 和带静态障碍绕行；随后重启并重定位后重复。每个用例记录目标、路线、位姿轨迹、实际终点、停止状态和用户可见结果。验收门槛为测试路线连续 10 次无误报到达、无碰撞、无失联后继续行走；未达标时不开放自由探索长距离移动。

### 阶段 4：将同一导航能力接回自主模式

**涉及：**`agentcore/mode/free_explore.py`、Go2 Card 能力描述与 PWA 展示；`reactive.py` 无需导航改造。

- [ ] `free_explore` 只在已定位且目标属于已知自由区时提议移动；LLM 负责挑选探索方向或已命名地点，不能覆盖导航器的可达性和完成判定。
- [ ] 对未知边界只记录“待探索方向”，先人工扩图或在受控探索模式中增量建图；不能把未知当空地。
- [ ] `reactive` 继续只做姿态与转向，不用它承担目的地导航。主聊天、设备页、探索模式使用同一套任务结果语义。

**验收：**LLM 选择被挡方向、远处物体或旧地点时，运动层均拒绝并给出可理解的原因；合法目标才执行，最终回复与真实导航终态一致。

## 交付与风险控制

- 每阶段保留小范围代码提交和针对真实失败路径的测试；静态算法测试不能代替实机验收。
- 保存每次导航的 `task_id`、地图版本、起终点、定位质量、路线与失败原因，便于复盘“规划错”还是“定位错”。
- 不修改 ESP32 的 MQTT 控制面、PWA 发现机制或 Go2 的机身避障逻辑；Go2 数据面继续使用现有 HTTP/WebRTC。
- 若阶段 1 证明现有 WebRTC 点云不适合重定位，先补传感器数据接口再继续；此时仍可交付阶段 0 的安全短距导航，但不得宣称已具备跨重启的指定地点导航。
