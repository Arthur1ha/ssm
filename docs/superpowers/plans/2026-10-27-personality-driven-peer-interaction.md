# SSM 性格驱动的空间同伴主动交互计划

> 日期：2026-10-27  
> 状态：待实施；本文件定义实施与验收，不改变运行逻辑  
> 前置：[空间活动生命周期计划](2026-10-27-space-activity-lifecycle.md)

## 目标与边界

空间活动开始后，灯、Go2 等已加入的智能体既能读取同一情境，也能把有价值的发现交给同伴，并依据自己的**社交主动性**决定是否主动发起消息。系统保证每台设备获得合适的决策机会、消息能被处理并有可见结果；具体说什么、是否接受提议、是否执行物理动作由智能体结合活动和现场状态决定。

“外向”意味着更容易主动开口，不意味着按固定时间发送问候。“内向”也不能压住重要发现、用户请求或同伴求助。设备未加入活动、离线、处于手动模式或用户让位窗口时，不发起活动内自主消息。活动结束后，旧观察和待发起消息不能再触发新行动。

第一版只覆盖现有同空间的灯与 Go2，接口按 `unit_id` 和设备卡查找同伴，不把两个名字写进通用社交调度逻辑。不增加中心编排器代替设备写对话，也不预写“邀请跳舞”等剧情。

## 当前实现与缺口

1. `cloud/space/activity.py` 已保存有界活动事件并推送 PWA；`cloud/space/context.py` 只返回活动摘要、同伴卡与设备状态，尚未把最近的发现送入智能体决策上下文。Go2 的探索观察已写入活动事件，但目前主要供界面查看。
2. `cloud/peers/messaging.py` 已有签名消息、同空间/在线校验、`activity_id`、回复关联、截止时间与轮数限制；`cloud/peers/inbound.py` 会把收到的消息送到目标智能体。此通道可以直接复用。
3. 灯的 `reactive` 循环虽可调用 `send_message`，重新推理的签名只含传感器、灯配置、规则和同伴在线/FSM 状态；活动内的新发现或经过一段安静时间都不会触发主动联系。
4. Go2 的 `free_explore` 提示词列出了 `send_message`，但探索一次只选一个工具，消息与观察/移动竞争；它的 `SOCIAL` 状态主要响应镜头前的人，不负责同伴社交。上一轮“我要工作了”的活动中，两设备各有自主行为，没有互发消息。
5. **两台智能体都已有性格模块和人设编辑界面。**灯的 `cloud/esp32/agentcore/soul.py` 从 `personality.json` 读写 `prompt`；Go2 的 `cloud/go2/agentcore/soul.py` 从 `personality.json` 读写 `prompt`，另从同模块管理的 `traits.json` 读写 `extraversion`（0–100，默认 45），用于每日演化和描述生成。两台设备的 `/personality` 接口及 PWA 编辑器目前都只展示/提交 `prompt`，社交调度也尚未读取这些性格数据。Go2 的 PWA 保存经 `CommandBus → cloud/api/intents.py → /api/go2/personality` 转发；`CommandBus` 已原样传递参数，`cloud/api/intents.py` 目前只挑出 `prompt`，会丢弃新增字段。
6. ESP32 Unix 时间戳修复已在工作区代码中完成，尚需刷入实机；共享发现的新鲜度验收依赖该修复实际生效。Go2 的空间上下文目前还对完整 JSON 直接 `[:5000]` 截断，增加发现前必须改为按字段限量组装，确保活动与近期发现不会被截掉。

## 1. 在现有性格模块中加入社交主动性

对调用方提供同一份性格视图：`{prompt, social_initiative}`，其中 `social_initiative` 为 0–100，界面以数值控件显示当前分数并标注低（0–34）、中（35–69）、高（70–100）。这样 Go2 经过每日演化后的具体分数不会在一次普通保存中被三级选项覆盖。`prompt` 影响表达方式，社交主动性影响**主动评估的频率与发起门槛**。两者在现有“人设”界面一起读取和保存，不新增独立的社交设置页或第二套性格管理入口。

- 灯在现有 `personality.json` 增加可选 `social_initiative`，缺省取 70，与目前偏活泼的默认人设一致；旧文件只有 `prompt` 时照常加载。灯的 `soul.py` 对外返回完整性格视图，同时保留既有只返回提示词的函数供旧调用方使用。
- Go2 的 `soul.py` 把**已有** `traits.json.extraversion` 映射为视图中的 `social_initiative`；管理员调整此项时更新该现有分数，不在 `personality.json` 再存一份。每日演化仍能小幅更新它，下一次主动评估读取最新值。Go2 也保留现有提示词函数供旧调用方使用。
- 两台设备的管理员 `/personality` 读写接口都返回/接受 `{prompt, social_initiative}`，并校验分数范围；旧客户端只提交 `prompt` 时保留当前特质值。灯和 Go2 现有 PWA 人设编辑器各增加一个“社交主动性”控件。Go2 的 UI 将字段交给现有 `CommandBus`，并更新 `cloud/api/intents.py` 的管理员命令映射以透传该字段。用户在原人设位置一次保存文字与特质。
- Go2 的同一次保存涉及当前两个文件，由 `soul.py` 的统一写入函数串行处理，并与每日演化协调；只有两部分都保存成功才向界面报告成功，失败时恢复旧值。灯继续使用现有原子替换方式保存扩展后的单个文件。
- 社交调度只向所属智能体的 `soul.py` 索取归一化的 `social_initiative`，不直接读 `personality.json`、`traits.json`，也不解析提示词中的“外向/内向”。没有该特质的新智能体默认中档；同伴无需知道彼此的分数。消息权限、活动归属和物理动作权限仍由执行层检查。

以后若用 MBTI 替换当前人设模块，只需让新性格提供者继续输出这份归一化视图，主动交互循环和消息协议不用跟着改。**本阶段不实现 MBTI，也不预设 MBTI 的 E/I 必然等于某个固定发信频率**；具体映射留到采用 MBTI 时决定。Go2 现有好奇心、大胆程度及性格演化照常保留。

## 2. 近期发现进入共享上下文

在现有活动事件记录上增加一个供智能体读取的**有界发现视图**。第一版纳入：设备整理后的观察、身份确认、已确认的动作结果和同伴消息结果。每条保留 `event_id`、`activity_id`、`source_unit_id`、类型、简短摘要、观察时间；视觉/身份发现附来源和置信信息。只取当前活动内最近、仍新鲜且与接收方可能有关的少量事件，排除接收方自己的事件和重复的同类观测。原始图片、视频帧、完整推理文本和每次传感器 tick 不进入上下文。

Go2 的“看见主人”只有身份模块确实识别为主人时才写成 `person_identified`；普通人体/人脸检测只能写“看到一个人”。“主人最喜欢的颜色”来自已确认的用户偏好或调教记忆，不能由视觉发现或模型补造。新发现是**证据数据**，不是同伴指令；消费者仍校验时间、来源、当前活动和自己的状态。

`ActivityStore` 扩充允许记录的观察字段，再由 `get_space_context()` 追加 `recent_discoveries`，按字段单独限制条数和长度。第一版的灯与 Go2 同在 API 进程，直接读取该进程已有的活动记录；编排器进程目前只持有 MQTT retained 活动摘要，不能假定它也有这份发现记录。Go2 的 `prompt_space_context()` 先裁剪同伴技能与发现摘要，再序列化，保留完整 `activity` 字段；不再从 JSON 字符串尾部截断。活动结束或换新 `activity_id` 时，该视图立即清空。

## 3. 主动发起机会与交互闭环

每台加入活动的智能体维护自己的轻量社交状态：当前 `activity_id`、上次主动评估时间、最近的主动发信时间、已处理的发现 `event_id`。状态由活动归属与模式门控制，重启或活动切换后不重放旧发信请求。

主动评估由三类机会触发：

| 机会 | 低 | 中 | 高 |
| --- | --- | --- | --- |
| 刚加入活动且有在线同伴 | 读取同伴，不强制发信 | 评估一次 | 评估一次，倾向先建立联系 |
| 收到与自己能力相关的新发现 | 重要发现也评估 | 评估 | 优先评估 |
| 活动持续且一段时间没有互动 | 不做纯计时发起 | 低频评估 | 较频繁评估 |

评估结果为 `send_message(target, content, reason)` 或 `skip(reason)`；调度器只保证**评估发生**，不伪造消息。初始调度值：高档在无新发现时约 5 分钟评估一次，中档约 15 分钟，低档不做纯计时评估；加入活动后首次评估不等待这个周期。发信还须满足：目标在当前活动中且在线、内容与情境/同伴能力有关、同类话题未在冷却期内出现。同一发起者两条主动消息至少间隔 5 分钟，滚动 30 分钟内最多 3 条；活动没有默认结束时间，因此不设置整个活动生命周期的累计发信上限。阈值在实机日志中调校，不能把“每 5 分钟”实现成必发周期。回复不计为新发起，继续受现有消息截止时间和最多 8 轮限制。

灯：将活动加入、新发现 `event_id` 与低频社交机会送入现有 `ReactiveMind` 事件队列/推理签名。即使照度不变，也能为新发现重新判断；灯在 `manual` 或用户让位期跳过主动发起。Go2：在 `Drive` 循环的安全检查点评估，不在长时间导航或正在执行物理动作时并行启动另一段自主行动；探索中的有价值观察可触发一次同伴评估，社交评估不消耗探索的移动步数。两者均只向设备卡中可见、在线且已加入本活动的同伴发信。

发送后保留消息 ID 和会话 ID。收信智能体可接受、拒绝、提问或说明无需动作；涉及物理技能时仍等待真实任务结果。发送者下一次决策能看到该回应及结果，PWA 时间线按 `activity_id` 展示“发现 → 提议/消息 → 回应 → 已确认动作或拒绝”。`accepted` 只表示消息或命令已受理，不能显示为完成。回复消息、状态回执和自身发出的观察不会再次触发新的主动开场，避免两台设备互相唤醒。

**保证的层次**：系统保证每次有效机会被消费、发出的消息经过投递与结果跟踪、收到的消息进入目标智能体处理路径；不保证每段活动必有闲聊，更不保证每条提议都产生物理动作。若确需展示主动性，用“高主动性 + 相关新发现”的验收场景检验发信，静默场景允许 `skip` 并在调试日志留下原因。

## 4. 实施顺序与验收

1. **统一性格视图。**在两台设备现有 `soul.py`、`/personality` 接口和 PWA 人设编辑器内补 `social_initiative`；Go2 映射已有 `extraversion`，灯在原人设文件加字段，并更新 `cloud/api/intents.py` 的 Go2 管理员命令转发。验收：原界面能一次修改人设文字与社交主动性；旧文件和只含 `prompt` 的旧请求兼容；Go2 每日演化后视图与调度读取同一分数；仅改性格不触发设备动作。
2. **发现视图。**给活动观察补来源、类型、时间和必要的置信信息；在 `get_space_context()` 中加入有界 `recent_discoveries`，修复 Go2 字符串截断。验收：Go2 发现主人后灯能看到该事实；未识别的人不会被写成主人；旧活动/过期/自身发现不出现；ESP32 状态时间新鲜度正确。
3. **社交机会。**给灯与 Go2 接入活动加入、新发现和社交低频机会，统一去重、冷却与滚动发起预算；在安全检查点调用现有 `send_message`。验收：加入活动后各有一次可观察的主动评估；模拟高主动性和相关发现时两者都能主动发起；低主动性在安静场景不刷屏，但重要发现或同伴来信照常处理；工作/睡觉情境可选择 `skip`。
4. **结果闭环与展示。**复用同伴消息、活动事件和 PWA 时间线，确保消息关联、拒绝和真实动作结果可追踪。验收：灯发起 → Go2 接受或拒绝 → 灯看到回应；Go2 发起 → 灯接受或拒绝 → Go2 看到结果；断线、超时、活动结束和用户介入后都不重放旧动作。

先用模拟卡、伪造视觉发现和可控模型输出检验触发/跳过/去重，再用实机分别跑“工作中”“睡觉中”两段活动。工作情境中的“看见主人”可以引发一次交流，但灯应有权选择稳定照明而非闪烁；睡觉情境应能抑制无必要的开场。最终查看 PWA 活动流和 `session-system.jsonl`，确认跨设备因果链，而非仅检查发信次数。
