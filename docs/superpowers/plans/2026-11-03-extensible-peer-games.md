# 多设备互动与轻量玩法扩展计划

> 日期：2026-11-03  
> 状态：首个玩法 `color_hunt` 已接入；2026-11-09 改为依据共享上下文自主邀请和选色，并展示可追溯的选择依据；第二玩法未开放
> 范围：灯与 Go2 在已有空间活动中的自主互动；先实现“邀请玩游戏”，保留增加其他互动类型的入口

## 1. 目标

灯与 Go2 可以在同一空间活动中自主提出、接受或拒绝简单游戏。设备的常驻提示词只描述互动原则；每次决策时注入**当下可玩的玩法名称和一句玩法说明**。新增简单玩法时，加一项轻量入口和对应执行函数，不改通用消息流程，也不把玩法逐条写进灯或狗的固定提示词。

这里的“玩法”是程序里可调用的一段具体行为，**不建立游戏规则文件、规则 DSL、独立游戏引擎、游戏管理页面或第二套 Agent 运行时**。玩法中的多步决策继续由现有 LangGraph 和设备工具完成；执行函数只接入具体感知、动作和结果判定。

首个迁移对象是现有“狗根据灯的实时颜色找同色物品”。“找闪烁的东西”和“跟着灯走”作为后续玩法例子，只有所需感知与安全运动能力实测可用时才进入可玩列表；不能仅加入名称就宣称已经能玩。

## 2. 当前接线与待改之处

| 位置 | 可复用的现状 | 本计划要调整的部分 |
| --- | --- | --- |
| `cloud/api/activity.py`、`cloud/space/activity.py` | 用户启动活动，设备各自进入 `reactive` / `free_explore`；活动有统一 ID 与可见时间线 | 保持用户启动活动的边界；游戏只能在已加入的活动内发起 |
| `cloud/peers/messaging.py`、`cloud/peers/inbound.py` | 签名 MQTT 同伴消息、消息 ID、有限期限、投递/进度/结果和回复 | 在普通消息上增加可选的互动类型与玩法标识，复用原通道，不建第二种消息总线 |
| `cloud/peers/social.py` | 活动成员筛选、社交机会和频率限制 | 邀请继续受同一活动、在线状态与冷却约束 |
| `cloud/agents/lamp/workflows/reactive.py`、`cloud/agents/go2/workflows/social.py` | 灯与狗可自行决定是否给同伴发消息 | 决策前注入当前可玩玩法的简短列表；模型也可选择普通聊天或不邀请 |
| `cloud/agents/go2/workflows/free_explore.py`、`cloud/go2/mode/free_explore.py` | Go2 接受同伴消息后可进入任务；目前把 `follow_peer_color` 和 `color_object_game` 写在仲裁及执行分支里 | 仲裁只判断接受、拒绝、延后及所请求的互动类型；具体游戏由玩法 ID 找到执行入口 |

现有视觉目标导航计划允许对当前可见的静态目标做受限接近，但不等于能持续追踪移动的灯，也不等于能检测闪烁。实施时以当时真实的设备能力和现场验证为准。

## 3. 设计

### 3.1 互动类型和玩法入口

互动类型先保留 `message` 与 `game_invite` 两类。前者是普通同伴交流；后者表示“我提议玩某个游戏”。未来增加其他互动类型时复用同样的活动、身份、回复和结果边界，不影响现有玩法。

建立一个进程内的轻量玩法表，每项只有稳定 `game_id`、显示名称、一句话玩法说明、适用参与者，以及一个执行入口。入口提供当前是否可玩的判断和执行方法；它可读取实时 Card/空间状态，但表本身不复制设备能力或维护持久状态。增加玩法只需在这一处登记并实现对应入口。别让模型输出任意 Python 函数名、MQTT topic 或未经登记的 `game_id`。

例子：

```text
color_hunt: 灯改变颜色，狗自主观察并可选择视觉目标导航 → Go2 现有 LangGraph 与工具
blink_hunt: 灯或场景中有闪烁目标，狗寻找它 → 待连续视觉证据可用后开放
follow_lamp: 狗跟随灯的指引或位置 → 先明确玩法并验证目标跟踪、地图和停步
```

这些是**代码入口示例**，不是要用户填写的配置项，也不是每个游戏必须实现的统一规则模板。玩法可以有不同的内部步骤；通用层只负责邀请和结果关联。

### 3.2 动态注入与选择

- 在灯或 Go2 出现社交决策机会时，按当前 `activity_id`、已加入且在线的同伴、设备模式，以及玩法入口的可用性函数筛出可玩项。只把少量 `game_id + 名称 + 一句话说明` 注入本轮决策上下文，避免每次塞入完整规则和实现细节。
- 模型决定是否邀请、邀请谁、选哪个可玩玩法，并可用自己的口吻写邀请语。发送前由执行层重新核对活动、目标、冷却和 `game_id`，不信任模型输出的可用性。
- Go2 收到邀请时读取该玩法的简短说明与最新空间状态，自主决定接受、拒绝或延后。它不能因为 `game_id` 存在就跳过连接、模式、用户接管、运动安全和任务优先级检查。
- 具体玩法执行时再读取新鲜设备状态。提示词负责协商与逐步决策，设备工具和执行入口负责真实能力、步骤上限及事实判定。普通用户对话和管家单次指令不需要注入玩法列表。
- 灯与狗的固定提示词只保留通用原则：同伴消息是提议；可拒绝；一次一个工具；等待真实结果；不能凭邀请、模型文字或视觉描述宣称游戏完成。移除 Go2 当前写死的“变化灯色找同色物品 → `follow_peer_color`”分类文案。

### 3.3 消息与任务生命周期

继续使用 `ssm/agents/{unit_id}/message`。普通消息维持现有格式；游戏邀请在已签名的消息体上附加 `interaction_kind=game_invite` 与 `game_id`，正文仍是自然语言邀请。接收端验证两项为已知值，并核对发送者和接收者属于**同一当前活动**。旧普通消息缺少新字段时照常处理。

```text
灯选择可玩项 → 发邀请(message_id, activity_id, game_id)
狗收到 → 自主接受 / 拒绝 / 延后
接受 → 建立有期限的任务(task_id) → 逐步执行 → 回传真实结果
结束 / 用户介入 / 断连 → 取消或收束任务 → 活动时间线更新
```

消息 ID 用于去重和回复关联，任务 ID 用于动作回执；`game_id` 只标识玩法，**不授予设备控制权**。投递成功、接受邀请、开始执行和完成是不同状态。继续使用现有 `send_progress`、`send_result`、活动 SSE 事件及 PWA 时间线；不另做“游戏成功”客户端状态。重启、重复投递、过期消息不能重做物理动作。

用户仍是活动启动者；同伴消息和游戏邀请不能启动活动。灯保持 `manual/reactive` 边界与用户让位窗口；Go2 保持 `manual/free_explore`、急停、控制租约、地图和障碍检查。用户新操作结束活动后，游戏不得继续发动作；正在运动的 Go2 走现有停止与停稳核对路径。

## 4. 首个玩法及后续能力边界

**`color_hunt`：**进入活动不再固定等待十秒邀请。灯在现有社交机会中，依据用户要求、同伴状态和近期发现决定邀请、询问、普通交流或跳过；邀请必须给出简短理由并引用当前共享事实。Go2 可接受、拒绝或延后。接受后，灯通过现有 Graph 从真实环境观察中选一种易辨认的颜色，开灯和设色前校验观察引用，等待边缘回执；没有观察就如实结束。取消预设白色、蓝色和玩偶目标。狗重新观察，自选同色候选物，再调用现有视觉目标导航；仅 `ok` 与 `odom_stopped_and_visual_recheck` 同时成立才确认找到。候选选择及灯的选色、邀请在活动时间线上保存 `decision_basis`，用户可查看来源、时间和摘要。找到后结束本局，不自动变色、返航、关灯或执行姿态剧情。活动结束、用户接管、断连和期限边界保持有效。

**活动入场顺序（2026-11-09 修正）：**Go2 进入自由探索后立即获得第一轮观察与探索机会，后续再按好奇心评估；新鲜画面的场景描述写入现有活动记录，供灯读取近期发现。加入活动或经过一段空闲时间本身不产生主动社交机会；灯依据真实的新发现决定是否交流或邀请。普通聊天与行动建议继续使用统一同伴消息，由狗自主接受、拒绝或延后。自由探索按实时地图选择可达边界，不需要配置活动范围；定位或地图不可用时如实说明阻碍。

**`blink_hunt`：**若要狗“找闪烁的东西”，需先说明是灯自身闪烁还是场景中其他目标，并具备带采集时间、目标关联和连续帧明暗变化的观察。单帧照片或视觉模型的一句话描述不能证明闪烁。证据未具备时不列入可玩列表；可以保留普通对话提议并如实说明当前无法确认。

**`follow_lamp`：**桌面灯本身是固定设备。“走向灯”“跟随灯的位置”和“按灯光指引移动”是不同玩法，执行入口必须选定一种清楚含义。若要连续跟随光源或方向，需实测识别/跟踪、定位、安全通路与停步；现有静态目标接近能力不自动升级为跟随能力。未满足前不列为可玩。

## 5. 实施顺序与可见验收

每一步独立交付，尽量在五分钟内从活动时间线或日志看到结果；先用模拟消息和状态快照验证，再进行有人工接管的设备试验。保留工作区中已有的未提交改动，特别是当前视觉导航相关文件。

1. **轻量玩法入口与动态上下文。** 建立玩法表和可用性查询，只在灯/Go2 的自主社交决策中注入当前可玩项。验收：没有活动、对端未加入、模式不允许或能力不可用时列表为空；常驻提示词不再出现具体游戏名。
2. **通用邀请。** 在现有同伴消息上增加可选类型与 `game_id`，发送和接收都校验活动与登记项。验收：普通消息回归正常；灯可发一条游戏邀请；重复、过期、跨活动和未知玩法被拒绝；邀请本身不触发狗运动。
3. **Go2 仲裁和首个玩法迁移。** 将 `follow_peer_color` 特判替换为通用玩法选择；把已有颜色逻辑接到 `color_hunt` 入口。验收：狗可接受/拒绝；接受后任务 ID、步骤和结果可追溯；灯色过期或视觉证据不足时如实结束；自由探索恢复时重新读取地图和位姿。
4. **第二个简单玩法扩展验证。** 在感知与安全能力满足后新增另一玩法入口，验证无须更改灯/狗固定提示词、MQTT 互动流程和 PWA 活动组件。若选择 `blink_hunt` 或 `follow_lamp`，先完成第 4 节所述能力验证；不能通过放松结果判定来凑第二个示例。

完成定义：新增简单游戏只需要登记一项可玩入口及其执行代码；灯与狗从实时列表自主选择或拒绝；活动边界、消息关联、物理安全和真实回执仍由现有通用链路约束。没有感知证据的游戏不会显示为可玩，也不会被模型宣称成功。
