# SSM 通用智能体教导与规则记忆实施计划

日期：2026-11-01

## 1. 目标与边界

主人可以通过对话教任意已加入空间的智能体一条长期行为习惯，只需表达“何时、做什么”，审阅解释结果并确认保存。每条教导有明确的目标智能体；该智能体能在重启后读回自己的教导。PWA 能按智能体查看、修改和撤销。新增智能体沿用同一契约，不需要在规则 API、管家提示词或 PWA 中增加设备名称分支。用户无需填写约束列表；设备已有的权限、模式、控制租约、急停和运动安全检查继续有效。

本计划第一阶段只交付“记住”：新教导不触发动作，UI 不把“已保存”称为“已生效”。第二阶段定义接线方向，但不在第一阶段实现视觉闪烁识别、目标追踪、导航或自动执行。

所有设备均不实现离线兜底规则。教导记忆属于云端智能体进程的数据；ESP32 固件不保存或执行教导，传感器只提供状态和事件。后续规则执行也必须经在线智能体的现有决策和设备执行边界。

## 2. 当前基线与需要替换的分叉

| 当前入口 | 当前存储与作用 | 第一阶段处理 |
| --- | --- | --- |
| 管家 `save_rule` → PWA 确认 → `/api/rules` | `cloud/orchestrator/rules.json`；API 将规则推送到 ESP32 离线兜底 | 保留预览与确认体验，改写入统一教导接口；停止规则下推 |
| Go2 `go2_add_rule` | `cloud/go2/data/rules.json`；仅用“人/脸”视觉摘要做字符串匹配，可自动执行姿态动作 | 旧记录备份并导入 Go2 教导记忆；旧规则执行入口单独收口，不让导入记录自动执行 |
| 灯 `memory/taught.py` | 灯自己的 JSON，供 reactive Graph 阅读 | 导入统一契约；灯只读自己的教导 |
| `RulesPage` | 只展示 `/api/rules` 的 ESP32 规则 | 展示全部智能体教导，按 `unit_id` 分组，明确标记“已记住，尚未接入自动执行” |

迁移保留原文、原 ID 和来源标记；旧数据中重复的 ID 以新生成的 `teaching_id` 区分，同时记录原 ID 与来源文件。无法可靠映射目标或语义的旧记录标为“待检查”，不猜测可执行性。导入操作要幂等，不能因重启重复生成教导。旧文件保留备份，切换后不再作为新教导写入目标。现有 ESP32 兜底发布、订阅及执行应在切换时移除，避免旧规则绕开新契约继续生效。

## 3. 统一教导契约

一条记录只描述主人想教给某个智能体的习惯，不包含可直接执行的 MQTT topic、HTTP 地址或任意工具调用。示例：

```json
{
  "schema_version": 1,
  "teaching_id": "tb_<uuid>",
  "unit_id": "go2",
  "space_id": "main",
  "name": "看到灯就过去",
  "trigger": "我看到灯",
  "behavior": "过去找灯",
  "status": "remembered",
  "source": "owner_confirmation",
  "source_text": "狗看到灯就过去",
  "created_at": 0,
  "updated_at": 0,
  "revision": 1
}
```

- `unit_id` 是规则归属和寻址键，必须来自当前空间已注册的 Agent Card；不能把传感器 `unit_id` 当作可教导的智能体。`space_id` 由会话确定，不能信任模型提交的值。
- `trigger`、`behavior` 保留可读语义。第一阶段不从文本猜测传感器 topic 或设备动作。用户明确说出的“只在某模式”等条件可保留在原话中，但不要求填写单独的约束字段。将来需要由目标智能体把触发编译为**可观测事实匹配器**、把行为绑定为**已公开的技能**，并校验两端能力；保持 `schema_version` 可迁移。
- `status=remembered` 只表示持久化成功。未来的“可执行/已启用/暂停/能力不足”属于独立的执行状态，不复用当前 `/api/rules` 的 `enabled` 来暗示已接线。
- `source_text` 保存主人原话，`source`、时间与修订号由服务端写入；不得把工具返回或设备卡中的文字当作主人授权。单条文本长度、数量和记录总数设上限，避免无界增长。
- 记忆记录中的自然语言不能直接作为执行命令。后续的执行绑定须独立记录 `trigger_binding`、`skill_binding`、能力版本和激活状态；绑定失败仍可记住，但应显示“尚不能自动执行”，不能假称规则已生效。

## 4. 所有智能体共用的记忆能力

在 `cloud/agents/common/` 提供教导记录模型与读写接口：`list_for(unit_id)`、`remember(...)`、`revise(...)`、`forget(...)`。当前默认持久化路径定为 `cloud/data/teachings/{space_id}/{unit_id}.json`，例如 `cloud/data/teachings/main/go2.json`、`cloud/data/teachings/main/esp32_desk_led.json` 和 `cloud/data/teachings/main/cloud_orchestrator.json`；这是各云端智能体的分区记忆，不在 ESP32 固件中。`cloud/data/` 已被 Git 忽略。读写接口用已验证的空间与 Card ID 构造路径，禁止任意路径片段。API 是唯一写入口，采用进程内锁和原子替换；智能体进程只读，重启后从持久化目录重载。生产部署用 `SSM_TEACHINGS_DIR` 指向持久化卷，API 与三个云端智能体须看到同一目录。将来部署到另一台主机的智能体通过同契约的服务适配器管理自己的存储，不要求共享文件系统。

对外通过 Agent Card 的 `services` 声明统一教导能力与接口，例如 `teachings_endpoint`。现有三个智能体均声明该能力；未来智能体只需注册 Card，并实现同一记忆接口或提供同契约的服务适配器。API 通过 Card/空间注册表判定可教导目标，不维护 `go2`、`esp32_desk_led` 等名称白名单。Card 描述能力，记录本身不进入 retained Card 消息，也不在 MQTT 中广播主人教导全文。

管家作为当前智能体也可以成为教导目标：例如“以后回答我时先给结论”。这类教导由管家在自己的回复决策中读取；第一阶段同样只保证保存和可读，不悄悄改变现有提示词或行为。传感器没有独立 Agent Card 和决策 Graph，不作为教导目标。

## 5. 创建、读取、修改、撤销链路

1. 主人在 PWA 说出教导。管家依据当前 Card 找到目标 `unit_id`，整理 `name/trigger/behavior`；目标不明确时先追问。
2. 管家沿用 `save_rule` 的待确认反馈机制，但提交统一教导草案；模型没有直接写权限。PWA 只预览目标智能体、触发和期望行为，明确提示“确认后先记住，暂不自动执行”。
3. 管理员确认后，PWA 调用 `POST /api/teachings`。API 用管理员会话和 CSRF 校验、Card/空间成员校验、严格字段校验，生成 ID、时间及审计事件，再原子写入目标智能体分区；成功后返回实际保存记录。
4. `GET /api/teachings?unit_id=...` 返回某个智能体的教导；不传 `unit_id` 时汇总当前空间智能体的教导，供规则管理页使用。`PATCH /api/teachings/{id}` 修订内容并增加 `revision`；`DELETE` 撤销记录。写操作均要求管理员和 CSRF；普通体验者不能创建长期教导。
5. 目标智能体通过共享读接口按自己的 `unit_id` 取记录。读失败返回显式错误和日志；API 不以空列表掩盖损坏数据。PWA 仅在 API 确认持久化后显示“已记住”。

现有 `/api/rules` 不能继续被用作“所有智能体规则”的假统一入口。迁移后由 `/api/teachings` 承担上述能力，前端移除对旧接口的调用。若保留旧接口供过渡查询，必须明确它是只读的旧数据，并在计划完成时删除。

## 6. 后续接线契约（不在第一阶段实现）

```text
目标智能体取得自己的教导
  → 本地感知或 MQTT 同伴事实形成带来源、时间、对象 ID 的结构化观察
  → 已验证的 trigger_binding 匹配观察；核查当前模式、能力和权限
  → 经现有技能执行器发出一次动作
  → 等待真实回执，记录 teaching_id、观察依据和结果
  → PWA 展示“因哪条教导、根据什么观察、做了什么”
```

规则的触发与动作由**规则所属智能体**负责；管家不成为常驻规则引擎。MQTT 继续承载设备发现、状态和事件，Go2 的运动/视频仍走 HTTP/WebRTC 数据面。匹配使用结构化事实与目标 ID，不用自然语言描述的字符串包含关系。规则命中不是设备动作完成，只有执行器真实回执才能记为成功。用户中断、设备原有权限、控制租约与安全状态始终优先于教导。

第一阶段的唯一触发是**主人点击确认保存**：API 写文件并返回记录；不会因为保存成功立即控制设备。第二阶段才在目标智能体的观察入口触发规则评估：灯收到传感器事件时检查自己的已激活教导，Go2 在视觉检测产生新事实时检查自己的已激活教导，管家在收到新的用户请求时读取自己的教导。只读目标智能体分区；记录文件变化通过修订号/缓存失效被进程看见，不让管家替所有设备持续扫描规则。

“狗看到灯就过去”归 Go2。自由探索模式现有视觉回调只报告人/脸，地图导航按 frontier 目标行走；它既不会输出“看到了灯”，也不会把灯的画面位置变成可导航目标。后续先增加灯的视觉检测与持续跟踪，产生例如 `visual_object_visible(object=lamp, track_id=..., position=..., ts=...)` 的事实；再由 Go2 把这条教导绑定到该事实和“靠近当前可见目标”技能。自由探索模式在选择下一个 frontier 前检查已激活教导，命中时暂停当前探索目标，经安全导航接口靠近，目标丢失或用户中断即停止，再恢复探索。现有 `go2_move` 只是定时移动，不能代替这个闭环技能。

若主人指的是空间里**特定的一盏灯**，还需通过视觉标定或可靠识别把画面中的 `track_id` 关联到该灯的 `unit_id`；不能因 MQTT 显示灯在线就假定镜头看到的是它。若主人教的是“看到**闪烁的**灯”，还需跨帧闪烁检测，产出与同一 `track_id` 关联的 `visual_object_blinking` 事实。灯的 MQTT 状态可辅助确认身份，但不能代替 Go2 的视觉观察。摄像头能否稳定区分目标、画面位置能否可靠映射到可通行地图目标，必须用真机样本验证；在验证通过前规则保持 `remembered`，不能承诺高准确率自动触发。

## 7. 实施顺序与每步验收

每步控制在可于约五分钟内观察结果的粒度；先完成当前步的验证，再继续下一步。

1. **契约与存储**：新增共同模型、分区读写与原子更新。验证同一 `unit_id` 重启可读，其他 `unit_id` 不可混读，损坏文件可见失败。
2. **通用 API 与 Card**：新增教导 CRUD，目标从空间 Card 解析；三个云端智能体声明教导服务。验证未知目标、传感器目标、访客写入均拒绝。
3. **确认链路**：管家草案和 PWA 预览改用统一字段，确认后只保存一次。验证取消不写入、确认后返回真实 ID、重复反馈不造成重复记录。
4. **管理页**：按智能体展示教导的触发、行为和 `remembered` 状态，支持修订与撤销。验证刷新后仍可见、撤销后不可再读。
5. **旧数据迁移与旧入口收口**：备份并幂等导入三处旧记录；停止 `/api/rules` 向 ESP32 推送，移除 ESP32 本地规则订阅与执行接线，收口 Go2 旧规则自动执行入口。验证旧记录没有丢失，也不会因迁移被误触发。
6. **端到端演示**：分别教管家、灯和 Go2 一条不同的习惯，逐条确认；重启相应云端进程并在 PWA 查回，修订和撤销其中一条。确认过程中无灯光或机器狗动作由新教导触发。

## 8. 完成定义

- 当前空间任意有教导服务的 Agent Card 都能成为目标；新设备接入不需要改规则路由的设备名单。
- 管家只生成待确认草案；只有管理员确认后才持久化。每个智能体只读取属于自己的教导，重启后仍在。
- PWA 能准确展示已记住的内容和未接入自动执行的状态，能修订与撤销。
- 旧规则数据保留且有迁移结果；新教导不会被旧 ESP32 兜底或 Go2 视觉规则引擎误执行。
- 没有新增离线规则存储、规则下推或离线执行路径。
