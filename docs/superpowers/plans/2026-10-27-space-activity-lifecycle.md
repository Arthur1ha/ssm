# SSM 空间活动与设备持续交互计划

> 日期：2026-10-27  
> 状态：方案草案；本文件只定义后续实施，不修改运行逻辑

## 核心约定

用户向系统表达自己**现在进入或正处于一个会持续一阵子的情境**，例如“我要学习了”“我去睡了”“我出门了”，管家就启动空间活动。用户不需要点名设备、要求它们配合、给出结束时间或另行授权某种场景。活动没有默认时长；**下一次用户主动介入系统时结束**。管家将情境告诉设备并开启各自的自主模式，之后由设备自己感知、行动、交谈、提议和拒绝，不预写互动剧情。

“自由探索”是 Go2 当前模式名；灯没有同名模式。第一版对应为：Go2 进入 `free_explore`，灯进入 `reactive`。以后新增设备时，设备卡声明自己的自主模式，活动启动器按卡选择该设备的自主模式，而不是要求所有设备实现一个叫 `free_explore` 的模式。设备离线或不具备自主模式时，记录它未加入；其他设备照常运行。

## 1. 启动和结束边界

| 事件 | 活动行为 |
| --- | --- |
| 当前用户说“我要学习了”“我去睡了”“我出门了”等持续情境 | 建立活动，把原话中的情境作为共同上下文，启动在线设备各自的自主模式 |
| 用户没有再和系统交互 | 活动持续，不因固定计时器自动结束，也不需要续期 |
| 用户再次对系统说话、回复设备问题、发送新命令、手动控制设备或在 PWA 点结束 | 先结束当前活动、停止其自主模式，再处理用户的新请求；被动查看 PWA 不算介入 |
| 智能体互发消息、传感器变化或设备发起提问 | 不结束活动；这些都不是用户介入 |
| 单个设备离线、忙碌或自身安全检查阻止模式启动 | 该设备退出/未加入活动，其他设备继续；恢复连接后不盲目重发旧物理动作 |

第一版同一空间只保留一个当前活动。用户说出新情境本身也是一次介入：先结束旧活动，再以这次新话语启动新活动。用户明确说“停下”只结束活动，不再启动新的活动。**用户介入的判定在 API 接收已验证的新用户请求时完成**，包括主聊天、设备页对话、直接命令和模式控制入口；无需再靠编排模型判断旧活动是否应该结束。模型只负责理解这次新话语是否开启另一个持续情境。

活动与单次工具运行分开：`activity_id` 标识整段持续情境，`run_id/task_id` 标识其中一次决定或物理动作。活动结束后不再产生新的自主动作；已开始的 Go2 运动走现有停止路径并核对结果，不能把取消协程当作已停。灯收到用户命令时现有让位窗口继续生效。

## 2. 活动状态与设备模式

活动记录 `activity_id`、`space_id`、用户原话/情境、`started_at`、`revision`、`status`，以及每台设备的自主模式、实际切换结果、模式归属。**不记录 `expires_at`，不复用当前有会话期限的 `set_space_constraint` 充当活动本体。**活动摘要通过 MQTT retained 当前状态供各智能体读取；API 向 PWA 发送开始、设备加入/退出和结束事件，并提供当前活动的可见过程记录。

状态保持简单：`starting → active/partial → ending → ended`。模式启动必须回读确认；部分设备不可用则为 `partial`，管家不能把“已发送切换请求”说成所有设备都已进入自主模式。切换指令来自当前真实用户建立的活动；Go2 现有仅管理员可写的模式端点需要增加受控的活动切换路径，不能让模型伪造 `admin` 或让同伴消息替用户开启活动。现有设备连接、FSM、运动租约和急停检查仍在设备执行层生效。

活动拥有它启动的模式。用户介入时，先撤销活动模式，再执行新请求；结束逻辑仅改变**仍由本活动持有**且当前模式未被其他操作改写的设备，避免竞态覆盖用户选择。结束时把带更高 `revision` 的空活动快照写入 retained 主题。API/编排器重启后读取 MQTT 当前活动和真实设备模式进行对账；无法确认物理动作的结果保持未知，不自动重发。若用户介入事件与重启交错，介入事件的版本优先，旧 retained 活动不能重新启动设备。

### 2.1 `activity_id` 与现有 ID

`activity_id` 是**新增**的空间活动标识，建议使用 `act_` 前缀加随机 ID。它标识整段“学习中/睡觉中/出门中”，从开始到用户介入结束保持不变；前缀只是排查时便于识别，权限仍由服务端验证。同一活动会包含许多独立的消息、观察和动作，不能借用其中任意一个 `run_id` 或 `session_id` 充当活动 ID。

| ID | 范围和用途 | 与活动的关系 |
| --- | --- | --- |
| `space_id` | 哪个空间拥有设备和活动 | 活动归属一个空间；PWA 按当前空间读取 |
| `session_id` | 当前用户登录/对话会话，以及私人任务反馈 | 创建时可记录来源用于审计；活动不随原会话过期或 PWA 重开而换 ID，新的同空间有效会话仍可查看和结束它 |
| `activity_id`（新增） | 一整段持续情境 | 活动、模式租约和活动过程事件的共同关联键 |
| `trace_id` / `run_id` | 一次用户意图及某智能体的一次执行 | 创建活动的用户请求有自己的 ID；活动中后续每次决策/动作可有新的运行 ID |
| `message_id` / `conversation_id` | 一条设备消息及其往返对话 | 设备对话归到同一 `activity_id`，仍用消息 ID 判断回复关系 |
| `task_id` | 一次设备技能或物理动作 | 归到活动中，用原任务 ID 查询真实执行结果 |
| `event_id` | 一条 SSE/时间线事件 | 用于重连和去重；同一活动下每条可见事件都有不同 `event_id` |
| PWA `requestId` | 当前页面给一次用户发送请求配对气泡的本地计数 | 只在浏览器内有效，不发给设备，不作为活动或后端关联键 |

例如用户创建活动的请求属于 `session_id=ses_A`、`trace_id=tr_1`，得到 `activity_id=act_1`。过一会儿灯向狗发一条有独立 `message_id` 的消息，狗探索产生一个 `task_id`；它们在时间线中都带 `activity_id=act_1`。PWA 刷新后即使本地 `requestId` 重置，只要当前用户仍属于这个空间，仍可按 `activity_id` 读取同一段活动。活动模式的执行归属使用 `activity_id`，不依赖创建时的用户会话长期存活。

## 3. 自由交互与向用户求助

设备进入自主模式后读取同一活动情境，使用现有 `send_message` 与同伴沟通。灯可以邀请狗跳舞，狗可以接受、拒绝或继续探索；对话不是动作授权或完成证据。狗若接受，动作仍经过 Go2 自身当前模式、连接状态和执行器检查。现有 Go2 自主同伴策略只放行 `Hello`；要支持自主舞蹈，实施时需让当前活动范围内的无位移动作通过网关，保留设备急停和结果确认。

Go2 当前 `free_explore` 循环会探索、观察和执行动作，但尚未把“向灯提议”或“向用户发图片问题”接入探索决策。增加少量事件触发点即可：发现值得分享的事、同伴可能有帮助、遇到无法判断的问题。消息继续受现有长度、轮次和冷却限制，防止设备无限互聊。

狗需要用户辨认物体时，暂停相关探索，把问题和截图引用交给 PWA；图片仍走 HTTP 数据面。用户一回复，就是一次介入：**当前活动先结束**，再由狗处理回答。不会因为用户回答而悄悄恢复刚结束的自由探索；若用户希望继续，可通过新话语开启下一次活动。

## 4. PWA 展示活动过程

活动过程必须在 PWA 主屏实时可见，而不只存在于服务端日志。沿用当前 `ActivityFeed` 的对话气泡和状态样式，在一次活动下按时间呈现：活动开始/结束、设备进入模式、设备间消息、提议的接受或拒绝、探索观察、动作进度与真实结果、向用户提出的问题和截图。例子：

```text
学习活动已开始 · 灯自主调光中 · Go2 自由探索中
灯 → Go2：要不要跟着节奏跳舞？
Go2 → 灯：不了，我想去看看门口。
Go2 正在探索门口
Go2 看到了门边一个没见过的盒子
Go2 暂停探索：这是什么？ [查看截图]
```

这几类内容含义不同：消息气泡表示设备**说了什么**；状态行表示**实际进入的模式、正在做的动作及其结果**；观察卡片表示设备**看到了什么**。发送邀请不等于狗答应，狗说要探索不等于已移动；页面只能根据模式确认、任务回执和观察事件更新事实。展示经设备整理的观察摘要，不把模型内部推理、完整提示词、每帧视觉或原始传感器 tick 倒入活动流。普通设备回复仍归各自智能体署名。

为每条可见事件带上稳定的 `event_id`、`activity_id`、时间、发起设备、事件类型；同伴消息另带接收设备和 `message_id/conversation_id`，动作另带 `task_id`、状态，图片问题另带媒体引用。API 在**验证后的消息入口和实际设备结果处**生成空间可见事件，经现有 `/api/events` SSE 推给同空间 PWA；不能让浏览器直订 MQTT，也不能让前端凭日志猜设备做了什么。

普通界面显示“学习中”、设备名字、对话与状态，不把这些原始 ID 堆在气泡里；`activity_id` 等关联字段留在事件数据和开发排查视图中。UI 只用 `activity_id` 给活动分组、用 `event_id` 去重、用 `message_id/task_id` 对齐回复和结果。

PWA 打开或重连时，先读取当前活动及其最近的可见事件，再接 SSE，以 `event_id` 去重。现有 SSE 缓冲只按会话保留最近 100 条，主屏 `activityLog` 只在页面内存中，所以它们不足以让用户稍后打开 PWA 看到活动已发生的过程。活动侧保留一个有界的可见事件记录：始终保留开始/结束等关键节点，详细过程保留最近一段；它与调试日志分开，不保存原始图片或模型内部内容。

## 5. 实施顺序与验收

1. **活动状态。**在 `protocol/topics.md` 定义 `ssm/space/{space_id}/activity/current` retained 当前状态；API 提供启动/结束和 PWA SSE 事件；编排器用受控工具请求启动。验收：“我要学习了”产生一个无到期时间的活动；PWA 立即看到活动和各设备的实际加入状态；用户下一次发话使它结束；同伴消息不会结束或重启它。
2. **模式接入。**按设备卡/模式适配调用灯 `reactive` 与 Go2 `free_explore`，确认实际切换并记录归属；用户介入时先停自主模式再执行新请求。验收：两设备可分别成功/失败；离线狗不阻止灯；用户新命令不会与旧探索竞态。
3. **活动上下文。**`get_space_context()` 返回当前活动摘要；灯与 Go2 的自主循环读取它，发起的消息、动作和 UI 事件关联 `activity_id`。验收：不同情境传给设备的是用户实际表达的内容，不靠关键词规则写死“学习/睡觉/出门”动作。
4. **设备间自由交互与过程流。**在 Go2 探索循环接入 `send_message`，让灯和狗在模式内提议、拒绝、回应；把验证后的消息、观察摘要和动作结果关联到活动并发给 PWA；根据活动边界按需放行无位移的同伴动作。验收：PWA 能看到“灯邀请→狗拒绝→狗观察”的顺序；拒绝不产生动作，接受后仍等待真实结果；轮次和冷却限制有效。
5. **图片求助与重连。**Go2 暂停探索并发布带图片引用的问题；PWA 回答时先结束活动，再把回答送给 Go2。补活动过程的有界读取入口和 SSE 去重。验收：用户稍后打开 PWA 仍能看到最近的设备对话与探索节点；过期问题和已结束活动不能恢复运动；图片不放进 MQTT 消息体。

每阶段先用模拟设备和消息验收状态与停止行为，再做实机联调。继续沿用现有 MQTT 控制面、Go2 HTTP 数据面、ESP32 BSM/ISM/TriggerMap 边界。
